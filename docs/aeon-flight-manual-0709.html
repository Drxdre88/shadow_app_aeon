01 / Brains are replaceable. The notebook is not.

Permanent job. Replaceable secretary.

Astra reads the job, chooses a sensible approach and hands out assignments. Aeon holds the durable record. A small ordinary program handles waiting, process startup and supervision. Astra does not have to think continuously while nothing is happening.

1. You authorizeSave a draft, choose scope, then approve a launch or bounded plan.
2. Astra decidesRead the card; propose direct, planned or parallel work; save the decision.
3. Runner startsClaim queued work and start Copilot in the registered repository.
4. Agents deliverDo one bounded mission. Return evidence and a structured result.
5. You reviewReview the output. Approve the next phase or finish the workstream.
🧠

Astra gets the clipboard

Recommended model for the top-level mission leader and future secretary: gpt-6-astra. Your requested approach takes precedence. This is a role choice, not a claim that Astra has beaten every model in a benchmark.

🛠

Workers get the tools

Keep the existing Sol implementation/research workers and configured specialist reviewers. Selecting Astra for the parent does not require changing every subagent to Astra.

📚

Aeon keeps the notebook

Card revision, approved scope, routing decision, attempts, questions and deliverables survive the secretary process. A replacement reads that record, rather than guessing from an old conversation.

Today versus the target: today, you launch a card and the runner starts its chosen model directly. There is no automatic secretary-before-dispatch step. A saved conversation, /keep-alive or /every is not crash recovery. The target adds supervised, bounded secretary turns and reconciliation around the existing queue.

03 / Recommended implementation order

Six steps. No orchestration cathedral.

  1. Pin Astra and prove one supervised flight.

    Use Copilot + Astra explicitly, concurrency one, known repo, manual launch. Pass the no-file handshake before relying on any automatic routing. Owner: runner configuration and operator.

  2. Make delivery trustworthy before useful work.

    Preserve full reports before disposable checkout cleanup. Make commit/push permissions explicit; add result rules per objective. Map review to Landing Zone, questions to Live, and Done to your approval. Owner: result handling, storage and lifecycle.

  3. Add a small, visible execution policy.

    Separate objective from route: auto, direct, specialist, plan-then-execute, swarm, execution-only. Record your preference, selected route, reason, model roles, worker cap and time budget. Execution-only needs an approved current plan. Owner: shared validators and mission editor.

  4. Build Astra's replaceable secretary turn.

    On authorized work, read the latest card/plan/results, classify once, persist the decision and enqueue only approved scope. On completion, summarize or propose the next phase. Persist attempts and decisions outside the model. Owner: orchestration service.

  5. Make restarts safe, then make startup automatic.

    Add restart reconciliation, dispatch identifiers, bounded retries and stale-worker visibility. Never rerun an ambiguous attempt until its process and side effects are resolved. Host one supervised worker on Windows Task Scheduler or a service; test restart with only disposable missions.

  6. Expand gradually, with one integration owner.

    Start with two independent missions, then increase only after results, limits and cleanup work. Keep one coarse workstream card; phases/checklists and session records hold the breakdown. No automatic explosion of micro-cards, no self-merge.

Your approachWhat the secretary should do
DirectOne understood chain, one agent. Do not add a planning committee.
SpecialistOne domain expert for localized specialist work.
Plan then executeResolve uncertainty and coupling first. Stop at planning unless execution was also authorized.
SwarmParallelize independent lanes with disjoint ownership. Start with at most three workers inside a mission; integrate once.
Execution onlyFollow the approved plan, do not silently redesign it. Surface a blocker if the plan no longer fits.

Those routes are proposals, not currently accepted card fields. Start with simple policy and real observations; do not use arbitrary file counts as safety gates. Mission concurrency and subagent concurrency are different limits.

04 / Cold-start checklist

You have Aeon open. Nothing else.

Assumption: you are using hosted Aeon, not localhost:3000. The app can stay in your browser. We will open one runner terminal and one PowerShell window for checks. Copilot is started by the runner when needed.

Before starting anything: inspect all queued coding sessions for the runner's account, across all projects. The worker claims the oldest eligible card sessions; it is not restricted to your visible board. Cancel only your own unwanted test missions. Do not start it with an unknown backlog, and do not assume a guaranteed 15-second cancellation window.
  1. Check tools and Copilot sign-in.

    Open PowerShell. These commands do not start a mission. The CLI must be installed and signed in on this Windows account. If needed, open copilot, use /login, then /exit. Also confirm your Git origin access for the target repo.

    PowerShell / inspect only
    $repo = Join-Path $HOME 'data_science\dev_26\shadow_app_aeon'
Set-Location $repo
node --version
npm --version
git --version
copilot --version
Test-Path '.\node_modules'
Test-Path '.\apps\kairos-worker\runner.env.bat'
Test-Path '.\apps\kairos-worker\repos.local.yaml'

    If the launcher reports missing dependencies, restore the repository's existing dependencies before continuing. Do not run package installs inside a mission: its dependency folders may be shared with your live checkout.

  2. Check the two local configuration files.

    runner.env.bat needs the hosted Aeon address and an Aeon API key belonging to the user who launches the card. Keep the key only in that local ignored file; never paste it into a card, transcript or this page. repos.local.yaml maps the chosen slug to an existing local Git checkout. Confirm its base branch and avoid dependency-changing setup commands for these tests.

    First-time setup, only if a file is missing

    In apps\kairos-worker, copy runner.env.example.bat to runner.env.bat and repos.local.yaml.example to repos.local.yaml. Fill in the real values locally. Never overwrite an existing configuration with the example.

  3. Make the pilot explicit and small.

    Before a real test, edit only these non-secret entries in runner.env.bat, preserving everything else. A card's explicit model overrides the runner default. The global model for your ordinary Copilot chats stays unchanged.

    Lines in runner.env.bat / not PowerShell commands
    set KAIROS_COPILOT_DEFAULT_MODEL=gpt-6-astra
set KAIROS_MAX_CONCURRENT=1

    These are proposed manual edits; this HTML has not applied them. Keep this first pilot local to a trusted host/network. The worker still exposes a push endpoint even in poll mode; do not publish its HTTP port or expose an unauthenticated endpoint. Least-privilege hosting is a gate before unattended operation.

  4. Start the existing launcher and leave it open.

    Only after inspecting the queue. This loads the local configuration and starts poll mode. You do not need npm run dev for the hosted app.

    PowerShell / starts the runner and can execute queued missions
    Set-Location (Join-Path $HOME 'data_science\dev_26\shadow_app_aeon')
& '.\apps\kairos-worker\start-hangar-runner.bat'
  5. Check the launcher URL, not a guessed port.

    The normal launcher defaults to 8790; starting the Node service directly defaults to 8787. Follow the health URL printed in the runner window if overridden. In another PowerShell window:

    PowerShell / read-only health probe
    Invoke-RestMethod 'http://localhost:8790/health' |
  ConvertTo-Json -Depth 5

    Look for ok: true, mode: poll, a worker ID and a recent lastPollAt. A recent poll timestamp proves an attempt, not successful authentication. Check the runner log for 401/403/429 or network errors; the first claimed mission is the end-to-end proof.

  6. Prepare one disposable test card in Aeon.

    Use a clearly labelled test card on an authorized board in a realm with the repo registered. Keep this out of ordinary production work. For AI Mission Control, test sessions belong to the Hangar workstream rather than becoming a new backlog of micro-cards.

    Open board settings and enable Auto AI if needed to reveal the AI-card UI. Use the AI option when adding a card, or its context-menu mission editor. Choose Recon / aeon / copilot / gpt-6-astra. Keep Auto-run on drop OFF. Save is not launch. Start with T01 below.

Shutdown rule: finish or cancel your test missions through Aeon, wait for the runner to release the child processes and complete cleanup, then stop the idle runner with Ctrl+C. Do not treat closing a terminal as a reliable mission-cancel protocol. The launcher's clean-kill comment is not a substitute for that check.

T10 / SMALL FLEETAfter single-flight gates

Two flights. Still one notebook.

  1. After T01-T06 pass, make sure the queue is clear and all test missions are terminal.
  2. Stop the idle runner, set concurrency to two, and restart it.
  3. Launch two distinct no-file handshake cards with different markers. Observe whether their running intervals overlap.
  4. Confirm two distinct sessions/results and no change to your active checkout.
  5. Finish/cancel both, then restart the idle runner. No finished work should be re-dispatched.
Pass looks likeBoth markers land on the correct cards, observed overlap supports concurrency, and restarting an idle worker does not duplicate work. If sessions finish too quickly to overlap, record concurrency as unproven, not failed or passed by assumption.

This is not an active-process crash test and does not prove automatic startup after reboot. Those remain acceptance gates for the supervised secretary service.

06 / The receipt matters as much as the flight

What should land on your card?

ObjectiveAgreed deliverableCurrent caution
Bug fixRoot-cause fix, reproduction evidence, commit and honest checks.Runner can push the branch. Permission and actual delivery must be explicit.
ImplementRequested feature, mission commit, verification and limitations.Success must mean usable output, not only that the process exited.
ReconEvidence-backed report; verified versus inferred findings.Full report retention is not yet safe to assume.
AnalysisOne recommendation, trade-offs, supporting evidence and risks.A path plus a short summary is not delivery of the whole analysis.
PlanExecutable plan, dependencies and suggested next missions.Suggestions are not authorization and do not currently auto-launch.

The final fenced JSON block already carries status, outcome, summary, branch, commit, artifact paths, checks, questions and suggested tasks. Keep this engine-independent. Add a version, card revision, attempt ID, routing reason, requested/observed model, persisted artifact references and approval state as the secretary is built.

Do not confuse three kinds of success: the process ended; the mission met its objective; you approved the deliverable. Today needs_input can still produce a succeeded session. Objective-specific rules are stronger in the skill instructions than in the current server envelope validator. These are implementation gates, not things a green badge proves.

Mission Control's intended flow

Cryo → Depot → Live → Landing Zone → Done. Blocked work stays Live with a visible question. Only your approval means Done.

What the handler does today

Automatic result-column movement only runs for a dedicated boardMode=hangar board and searches for Landing or Tower. Normal Auto AI boards still get result metadata, but need lifecycle mapping before automatic Mission Control movement is dependable.
