# Aeon Brain — MCP Tools + REST Parity

**Phase 1 scope.** Four MCP tools, four matching REST routes, one shared Zod validator set, one shared data layer (`lib/data/memories.ts`). The MCP↔REST parity invariant from `CLAUDE.md` applies — a parity test mirroring `gantt-parity.test.ts` will lock both surfaces against drift.

---

## Tool 1 — `create_memory`

**Purpose.** The primary write path. Used by humans (manual notes), Claude (session summaries), voice (STT dictation), hooks (automated import).

```ts
create_memory({
  title:       string,                 // required, ≤ 255 chars
  bodyMd:      string,                 // required, markdown
  summary?:    string,                 // optional one-liner; auto-generated by caller if absent
  type?:       'note' | 'decision' | 'idea' | 'observation' | 'session_summary' | 'reflection',
  source?:     'manual' | 'claude' | 'voice' | 'hook' | 'import',
  sourceMetadata?: Record<string, unknown>,
  realmId?:    uuid | null,
  projectId?:  uuid | null,
  taskId?:     uuid | null,
  tags?:       string[],
  links?:      MemoryLink[],
  pinned?:     boolean,
}) → { id, title, type, source, createdAt }
```

**Validation.** Title 1–255 chars. `bodyMd` 1–100,000 chars (a soft cap to keep `tsvector` indexing fast — split larger inputs into multiple memories). `realmId` / `projectId` / `taskId` must be owned by the calling user (verified via existing helpers). `links[*].target` must exist when `target_kind ∈ {memory, task, project, realm}`.

**REST.** `POST /api/v1/memories`

## Tool 2 — `search_memories`

**Purpose.** BM25 full-text search over title + summary + body, with cheap filters. The bedrock retrieval primitive for Phase 4's `prepare_context()`.

```ts
search_memories({
  query:       string,                 // required, ≥ 2 chars
  type?:       MemoryType | MemoryType[],
  source?:     MemorySource | MemorySource[],
  realmId?:    uuid,
  projectId?:  uuid,
  taskId?:     uuid,
  tagsAny?:    string[],               // OR-match
  tagsAll?:    string[],               // AND-match
  pinnedOnly?: boolean,
  limit?:      number,                 // default 20, max 100
  offset?:     number,
}) → {
  hits: Array<{
    id, title, summary, type, source,
    rank: number,                      // ts_rank score
    snippet: string,                   // ts_headline excerpt
    createdAt, updatedAt,
    realmId?, projectId?, taskId?,
    tags: string[],
  }>,
  total: number,
}
```

**Query plan.** `to_tsquery('english', websearch_to_tsquery(...))` against the `fts` GIN index, ranked by `ts_rank_cd`, with `ts_headline` for snippets. Filters compose as plain `WHERE` clauses ahead of the FTS predicate.

**REST.** `GET /api/v1/memories/search?q=…&type=…&limit=…`

## Tool 3 — `link_memory`

**Purpose.** Add a typed edge from one memory to another entity. Edges are stored on the source memory's `links` jsonb.

```ts
link_memory({
  memoryId:    uuid,                                // source
  target:      uuid | string,                       // target id (or URL when targetKind = 'url')
  targetKind:  'memory' | 'task' | 'project' | 'realm' | 'url',
  type:        'relates' | 'supports' | 'contradicts' | 'supersedes' | 'refers_to' | 'blocks_thinking',
  note?:       string,
}) → { memoryId, link: MemoryLink, linksCount: number }
```

**Validation.** Source memory must be owned by the user. Target (when not `url`) must be readable by the user (memory: same user; task/project/realm: existing `verifyProjectAccess` / realm-membership check). De-dup: if an edge with the same `(target, targetKind, type)` already exists, return it unchanged.

**REST.** `POST /api/v1/memories/[id]/links`

There is a paired `unlink_memory` REST route (`DELETE /api/v1/memories/[id]/links/[linkIndex]`) but no MCP tool in Phase 1 — Claude rarely needs to delete edges, and the missing parity is documented in the parity test exclusion list.

## Tool 4 — `get_memory_with_neighbours`

**Purpose.** The graph-walk read. Returns a memory plus its 1–2 hop neighbours, ready to drop into a context window. This is the seed for Phase 4's `prepare_context()` — that later tool wraps this one with budget-aware compression and BM25 seeding.

```ts
get_memory_with_neighbours({
  memoryId:    uuid,
  hops?:       1 | 2,                  // default 1
  includeReverse?: boolean,            // default true — also fetch memories that link TO this one
  limit?:      number,                 // default 20 neighbours total
}) → {
  memory: Memory,                       // full record with body_md
  neighbours: Array<{
    memory: { id, title, summary, type, source, createdAt },  // slim shape
    edge: { type, direction: 'outgoing' | 'incoming', note? },
    distance: 1 | 2,
  }>,
}
```

**Query plan.** Recursive CTE: seed = `{memoryId}`, expand by unnesting `links` (outgoing) and joining `memories WHERE links @> jsonb_build_array(jsonb_build_object('target', $1))` (incoming). Cap at `limit` neighbours per hop. Returns slim neighbour shape — no full `body_md` — to keep the response packable.

**REST.** `GET /api/v1/memories/[id]/neighbours?hops=2&limit=20`

## Auxiliary REST routes (no MCP counterpart)

Phase 1 ships these on REST only; they are too admin-y for an AI to need:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/memories` | List/paginate (no FTS — use `/search`) |
| `GET` | `/api/v1/memories/[id]` | Read full memory |
| `PATCH` | `/api/v1/memories/[id]` | Edit title / body / tags / pinned / archived_at |
| `DELETE` | `/api/v1/memories/[id]` | Hard delete (`PATCH archived_at` is the soft alternative) |
| `GET` | `/api/v1/memories/[id]/export` | Render canonical `.md` (see `03-markdown-format.md`) |
| `GET` | `/api/v1/memories/export` | Stream all memories as zipped `.md` tree |
| `POST` | `/api/v1/memories/import` | Bulk import from a zipped `.md` tree |

The two `export` routes are the markdown round-trip — they make the canonical-md principle real, not aspirational.

## Shared layer wiring

```
lib/data/memories.ts          ← pure DB queries (Drizzle + raw FTS SQL)
   ├─ findMemoryById(id, userId)
   ├─ listMemories(userId, opts)
   ├─ searchMemoriesFts(userId, query, opts)
   ├─ getNeighbours(memoryId, userId, hops)
   ├─ createMemory(userId, input)
   ├─ updateMemory(id, userId, patch)
   ├─ addLink(memoryId, userId, link)
   ├─ deleteMemory(id, userId)
   └─ exportMemoriesAsMarkdown(userId, opts)   // returns AsyncIterable<{path, content}>

lib/actions/memories.ts       ← 'use server'; auth + validate + delegate
   └─ thin wrappers that call lib/data/memories.ts after requireAuth()

lib/data/validators.ts        ← Zod schemas (createMemorySchema, searchMemoriesSchema, ...)

app/api/v1/memories/*         ← REST routes; call lib/data/ directly + authenticateRequest
app/api/[transport]/tools/memories.ts   ← 4 MCP tools; import same validators + data fns
```

`touchProject()` is **not** called on memory mutations — memories are user-scoped and do not belong to a project for invalidation purposes. The Pusher publish path adds a new `user-{userId}` channel for memory events (Phase 5 will use this for daily-briefing push notifications); Phase 1 ships the channel name in the broadcast helper but no listeners yet.

## Parity test (`memories-parity.test.ts`)

Mirrors `gantt-parity.test.ts`. Locks:

1. MCP tool count = 4 (`create_memory`, `search_memories`, `link_memory`, `get_memory_with_neighbours`).
2. Each MCP tool resolves to a REST route with the same Zod input schema (import equality).
3. Each MCP tool resolves to a function in `lib/data/memories.ts` (import equality).
4. Every mutation path checks `userId` ownership before write.
5. Documented exclusions: `DELETE /memories/[id]`, `PATCH /memories/[id]`, `GET /export`, `POST /import` (no MCP counterpart) and `unlink_memory` (REST-only by design).

A green parity test means MCP and REST stay in sync without manual coordination.
