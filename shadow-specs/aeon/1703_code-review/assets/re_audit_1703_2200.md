## Core Intent Assessment

Aeon is a Next.js project management app with Kanban board, Gantt chart, Canvas, and Trophy Room features. The architecture follows a clean three-layer pattern: server actions (auth boundary) -> data layer (DB operations) -> Zustand stores (client state). The security sprint addressed most critical issues from the first audit. The codebase is in substantially better shape.

- `src/lib/actions/canvas.ts` lines 25-52: `createCanvasNode()` passes data to data layer without `createCanvasNodeSchema.parse()`. The schema exists but is unused at the action boundary.

- `src/lib/actions/canvas.ts` lines 54-69: `updateCanvasNode()` passes through without `updateCanvasNodeSchema.parse()`.

- `src/lib/actions/canvas.ts` lines 78-101: `createCanvasEdge()` has no schema validation. No schema exists for edge creation. SourceNodeId/targetNodeId are not validated as UUIDs.

- `src/lib/actions/vault.ts` lines 24-39: `sendToVault()` accepts `taskId`, `daysTaken` without `sendToVaultSchema.parse()`. The schema exists but is unused.

- `src/lib/actions/vault.ts` lines 41-57: `sendBatchToVault()` accepts entries array without `batchVaultSchema.parse()`. The schema exists but is unused.

- `src/lib/actions/checklist.ts` lines 31-49: `createChecklistItem()` accepts title, groupName, orderIndex without schema validation. No checklist item schema exists.

- `src/lib/actions/checklist.ts` lines 51-82: `updateChecklistItem()` accepts state, status, title without schema validation. The `state` field is cast with `as 'unchecked' | 'checked' | 'crossed'` on line 73, which bypasses type safety entirely.

- `src/lib/actions/gantt.ts` lines 88-105: `createRow()` accepts name, color, orderIndex without any schema validation. No row creation schema exists.

- `src/lib/actions/gantt.ts` lines 107-116: `updateRow()` accepts name, color, orderIndex without schema validation.

- `src/lib/actions/projects.ts` lines 18-35: `createProject()` does NOT validate through `createProjectSchema.parse()`. The timeScale is cast with `as 'day' | 'week' | 'month'` on line 31, bypassing validation.

- `src/lib/actions/labels.ts` lines 43-52: `updateLabel()` accepts `{ name?, color? }` without schema validation. No updateLabelSchema exists.

**Summary:** Of 13 action files, only 4 (board create/update, labels create, dependencies add, gantt create/update, ganttViews create/update) consistently apply Zod. The remaining ~15+ mutation endpoints skip validation despite schemas existing for many of them.

## 2. AUTH CONSISTENCY AUDIT

### Server Actions
Every exported server action calls `requireOwnership(projectId)` or `requireAuth()` as its first operation. This is consistently applied across all 13 action files. **PASS.**

### REST API Routes (v1)
All 6 route files call `authenticateRequest(request)` and check `isApiUser(result)`. Project ownership is verified via `verifyProjectOwnership()` or `findProjectById(id, result.id)`. **PASS.**

### MCP API Route
Every tool handler calls `requireOwnership(projectId)`. The outer `withAuth` wrapper checks Bearer token or falls through to mcpHandler. **PASS.**

### Middleware
Middleware checks session cookies for non-public, non-API paths. API paths (`/api/`) are allowed through, with auth handled at route level. **PASS.**

### FINDINGS:

**[MEDIUM] F2: MCP auth bypass when AEON_API_KEY is unset**

In `src/app/api/[transport]/route.ts` lines 685-692:
```typescript
async function withAuth(req: NextRequest) {
  const apiKey = process.env.AEON_API_KEY
  if (apiKey) {
    const result = await authenticateRequest(req)
    if (!isApiUser(result)) return result
  }
  return mcpHandler(req)
}
```
When `AEON_API_KEY` is not set, the `if (apiKey)` block is skipped entirely, and the request proceeds to `mcpHandler` without any authentication. The `userId()` function on line 51-54 will still throw if `AEON_API_USER_ID` is not set, but the intent here is clearly that auth should always be enforced. The conditional should be inverted: always authenticate, only skip if explicitly in dev mode.

**[LOW] F3: MCP route userId() is a static env variable, not the authenticated user**

In `src/app/api/[transport]/route.ts` line 51-55, `userId()` always returns `process.env.AEON_API_USER_ID`. Even when `authenticateRequest()` successfully authenticates a Bearer token user, the MCP tools use the env variable user ID rather than the authenticated user's ID. This means all MCP operations always act as the same user regardless of who authenticates. This is likely intentional for a single-user MCP setup, but worth documenting.

An attacker could pass any string value.

## 4. HOOK EXTRACTION QUALITY

The ProjectContent.tsx was split into 6 hooks:

| Hook | Lines | Responsibility |
|---|---|---|
| useProjectData.ts | 189 | Data loading, polling, store hydration |
| useBoardHandlers.ts | 146 | Board CRUD, vault, archive handlers |
| useLabelHandlers.ts | 34 | Label CRUD + toggle |
| useDependencyHandlers.ts | 30 | Dependency add/remove with optimistic updates |
| useGanttHandlers.ts | 191 | Gantt CRUD, views, reflow, push-to-gantt, edit modal state |
| useCanvasHandlers.ts | 55 | Canvas node/edge CRUD |
| ProjectContent.tsx | 362 | View orchestration, header, tab switching |

### Assessment:

**[PASS] Clean separation of concerns.** Each hook encapsulates a domain (board, labels, dependencies, gantt, canvas). No cross-hook dependencies except useGanttHandlers taking `setActiveTab` and `triggerReload` as parameters.

**[PASS] No leaky abstractions.** The hooks return clean interfaces. State (vaultTarget, showArchive, ganttEditTaskId) is co-located with the handlers that use it.

**[LOW] F5: useGanttHandlers has too many responsibilities (191 lines).**
This hook manages: gantt task CRUD, gantt view CRUD, reflow/reset, task click -> edit modal state, push-to-gantt. It could be split into `useGanttViewHandlers` and `useGanttTaskHandlers`, but at 191 lines it is not critical.

**[LOW] F6: useProjectData has hardcoded `console.error` for error handling.**
Lines 91, 141, 168 use `console.error` for error reporting. These swallow errors silently for the gantt/canvas tab loads, while the board load at least surfaces an error UI. The gantt/canvas tabs fail silently.

**[MEDIUM] F7: useProjectData stores fetched data in external stores via side effects.**
Lines 27, 49-88 use `useBoardStore.setState(...)` to push data into global Zustand state from within the data-loading hook. This is a side effect that makes the hook less predictable. The dependency array on line 100 `[projectId, loadKey]` does not include `setGanttTasks` or `setRows`, which are referenced inside the effect but are stable Zustand selectors.

## 5. ARCHITECTURAL ISSUES

**[MEDIUM] F8: TaskBoard.tsx at 574 lines violates the 500-line maximum.**
Per CLAUDE.md rules, 500 lines is the absolute maximum per file. TaskBoard handles: DnD context, column drag, task drag, keyboard shortcuts, filter state, connect mode, edit modal, dependency tree, label picker, color picker, and layout rendering. It has 12 state variables and 12+ handler callbacks. This is the remaining "god component."

**[MEDIUM] F9: reorderTasks still uses Promise.all without transaction.**
In `src/lib/data/tasks.ts` lines 150-168, `reorderTasks()` fires N parallel UPDATE queries via `Promise.all` without wrapping them in a DB transaction. A partial failure leaves ordering in an inconsistent state. This was identified in the previous audit and flagged as "NOT yet wrapped in transaction." It remains unfixed.

Similarly, `src/lib/data/columns.ts` lines 100-112, `reorderColumns()` uses the same `Promise.all` without transaction pattern.

**[LOW] F10: Dynamic imports in data layer.**
In `src/lib/data/checklist.ts` lines 113, 119, `findTaskWithDetails()` uses dynamic `await import('./labels')` and `await import('./dependencies')` to avoid circular dependencies. This works but is a code smell indicating the data layer modules have implicit circular relationships.

**[LOW] F11: Inconsistent error propagation in hooks.**
All hooks use `.catch((err) => console.error(...))` which silently swallows server action failures. The user sees optimistic UI updates that never get reverted. The dependency handler (useDependencyHandlers.ts line 13-14) is the only one that implements proper rollback on failure.

## REQUIRED CHANGES (Priority Order)

### HIGH Priority

1. **Wire up existing Zod schemas at all remaining action boundaries.** For columns, canvas, vault, and projects actions, import and call `.parse()` on incoming data before passing to data layer. This is mechanical work: the schemas already exist.

2. **Replace `as` casts on action inputs with Zod validation.** In checklist.ts, ganttViews.ts, and projects.ts, the `as` casts should be replaced with proper schema validation. For checklist state, create a schema: `z.enum(['unchecked', 'checked', 'crossed'])`. For ganttViews groupBy/taskOrder, the Zod parse already handles this - remove the redundant manual casts.

3. **Create missing schemas** for: checklist item CRUD, row CRUD, canvas edge create, label update, reorder operations (task and column).

### MEDIUM Priority

4. **Fix MCP auth bypass:** Change the `withAuth` function to always run `authenticateRequest()` regardless of whether `AEON_API_KEY` is set. If no API key is configured AND no session exists, reject.

5. **Wrap reorderTasks and reorderColumns in transactions.** Replace `Promise.all` with `db.transaction()`.

6. **Break TaskBoard.tsx into sub-modules** to get under 500 lines. Extract DnD logic, keyboard shortcuts, and the modal/overlay section into separate components or hooks.

### LOW Priority

7. Replace `any` types in TaskBoard.tsx (line 120) and DragPreview.tsx (line 8) with proper interfaces.
8. Consider adding error boundaries or toast notifications for failed server actions instead of silent console.error.

## STRATEGIC ASSESSMENT

The security sprint made significant progress. Auth coverage is now complete across all three boundaries (actions, REST, MCP). Zod validation is correctly applied on the most critical paths (board tasks, gantt tasks, dependencies, labels create). The hook extraction from ProjectContent is well-executed with clean interfaces.

The remaining gap is that roughly half the mutation endpoints still skip Zod validation, and several `as` casts in server-side code create type-safety holes that undermine the validated paths. Closing this gap is primarily mechanical work since most schemas already exist.

The codebase passes the "return after 6 months" test for readability. The three-layer architecture (actions -> data -> stores) is consistently applied and intuitive. File sizes are reasonable except for TaskBoard.
