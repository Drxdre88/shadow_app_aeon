01 / Executive brief

A real mission interface.
A local execution foundation.

You wanted an operating surface for delegating meaningful work: choose a repository, give an agent an objective, let it use the right local tools, and receive an outcome you can inspect and accept.

The released system now has a distinct mission-card experience inside the dedicated AI Hangar: repository, objective, agent/model, instructions, draft and launch controls, status, and recorded results. A Repositories manager supplies the shared directory. An authenticated runner on your workstation retrieves queued work and starts a CLI agent against a locally mapped repository.

The missing product connection is environment readiness. A registered repository is not yet a fully provisioned execution profile. The workstation still needs a matching path, dependencies, usable CLI credentials and environment configuration. The other major gap is dependable delivery: a result can name a report or commit without guaranteeing that its files are hosted, published, independently accepted or recoverable after failure.

Available

Describe and launch work

Dedicated mission fields, idle drafts, deliberate launch, repository registration, live session visibility and a result section.

Operator-managed

Execute on your setup

A local runner uses your checkout, installed tools, account and data access. Mapping and environment preparation remain host configuration.

Next

Make outcomes dependable

Visible readiness, durable artifacts, recoverable runners and enforceable acceptance must precede routine unattended batches.

Recommended next investment: complete one repository-to-result experience. Make Swarm visibly ready, run a bounded mission, preserve its output before cleanup, and make the accepted result openable from the card. Use that as the template for ARQ and other repositories.

04 / The cloud–local boundary

Your machine does the repository work.

The browser saves intent in hosted Aeon. A running local worker connects outward to Aeon and asks for eligible work. The cloud does not reach into your laptop and activate a terminal when you open a card.

Events and outcome

Status, telemetry and a structured result are sent back. The card presents the result for operator review.

↩

File persistence and publication need separate proof.

Three independent identities

  • Aeon account/API key: which work the runner can claim and update.
  • Agent CLI login: which model account and entitlements it uses.
  • Repository/data credentials: what Git, databases and services the local process can access.

Signing into the website does not establish the other two.

Two separate inventories

  • Cloud registry: repository identity and permitted engines.
  • Host mapping: where that repository exists and how the host prepares execution.

These must agree. A repository listed in the UI does not prove an eligible, online host can execute it.

05 / Repositories, environments and skills

The registration-to-readiness gap.

What “register Swarm” actually means

The cloud entry gives swarm a name, Git URL and permitted engines in a realm. The worker separately resolves that slug in apps/kairos-worker/repos.local.yaml. The mapping points to an existing checkout on this host. It does not download a repository from the cloud entry’s Git URL.

Environment activation is not yet a reusable product feature. The local envSetupCmd executes in a separate shell before the agent. Changes to that shell’s environment—such as activate.bat, Activate.ps1, set or export—do not persist into the later agent process. Files created by setup can persist. The current agent inherits the runner’s own environment.

What works for environments today

  • Start the runner with the required tools already on its inherited path and the intended account authenticated.
  • Use an explicit interpreter or repository-supported environment command for mission operations. Swarm’s documented pattern is hatch run swarm_env_312:<command>.
  • Use local setup hooks for durable preparation such as dependency installation or file preparation. Do not rely on an activation-only command to change the later process.
  • Treat shared linked dependencies as shared resources. A junction supplies access; it does not isolate writes by different missions.

How the agent finds Swarm skills

The worker starts the selected CLI with the mission worktree as its working directory and supplies a brief that refers to the repository instructions, Aeon dispatch contract and objective skill. The CLI’s own trust and discovery mechanisms then determine which instructions and skills it can load. Aeon does not package every repository skill into each launch request.

On this host, Swarm’s canonical project skills live in .claude/skills; its .agents/skills bridge and the personal Copilot skills bridge expose shared sources to the relevant clients. The 21 September mission discovered all seven Swarm project skills. This is concrete evidence for that setup, not a guarantee that every CLI, worktree or future repository will discover the same skills.

ARQ has a local checkout and CLAUDE.md, but this inspection found no ARQ .claude/skills or .agents/skills directory. Selecting ARQ therefore cannot promise Swarm-like domain skill discovery. A future readiness preview should show the skills actually found by the intended runtime.

06 / End-to-end execution

One Swarm mission, step by step.

Example: “Investigate a Swarm behavior, use its relevant skills, and return a report with evidence.” This describes the current execution path; it does not launch the example.

  1. Operator / browser

    Create a mission and keep it idle

    Choose repository swarm, objective recon or analysis, engine, an available model and instructions. Save draft while setup is incomplete. State the intended outputs and acceptance criteria explicitly.

  2. Host / preparation

    Prepare the execution account and repository

    Confirm the host mapping, branch, environment command, required data access, skill visibility and model entitlement. The 22 September catalog offered Sonnet 5; the configured Opus 5 default and Sol reviewer were absent. Recheck availability at launch; do not silently substitute.

  3. Aeon / launch action

    Save & Launch queues the session

    The action validates the mission and access, stores a dispatch prompt and creates a queued session tied to the card. It records the session reference and disarms auto-run. A live-session uniqueness rule prevents simultaneous live attempts for one card.

    The queue insert and subsequent card update are separate operations. If launch reports an error, inspect sessions before retrying: a session may already exist.

  4. Workstation / polling

    The runner claims work over an outbound connection

    The foreground launcher loads ignored host configuration and starts the worker. The normal poll interval is 15 seconds. Claims are scoped to the Aeon API-key owner and compatible engines, currently oldest-first.

    Claims do not advertise the host’s repository list. A host can claim an unknown slug and fail it. There is no complete capability-aware host scheduler.

  5. Workstation / Git

    Resolve the slug and prepare a worktree

    The runner reads the local mapping and attempts to fetch origin. A first run uses the remote base when available, otherwise the local base; a rerun can reuse the card’s existing aeon/… mission branch. It creates a disposable worktree from that selected history.

    A failed fetch is a warning, so remote freshness is not guaranteed. Check the actual base revision. The worktree does not automatically include uncommitted changes from your editor’s checkout; configured file links/copies are separate.

  6. Workstation / setup and CLI

    Prepare files, then start the agent

    Optional local setup runs. The full instructions are placed in a temporary brief and the CLI gets a short pointer. The CLI runs with the worktree as its working directory and the runner’s inherited environment. The card model takes precedence over the runner default.

  7. Agent / repository work

    Read instructions, use skills, execute the objective

    The agent loads available repository and personal guidance, calls local tools, and uses the requested environment commands. Swarm can use its already-authorized data integrations because those tools and credentials are on the execution host, subject to what is available from the worktree.

  8. Runner → Aeon / observation

    Stream progress and return a structured result

    The worker forwards events and heartbeat updates, checks cancellation and extracts the result envelope. It reports summary, tests, branch/commit, artifact paths and questions. Coding completion claims with missing deliverables can be downgraded, but this is not a universal content review.

  9. Aeon / result handling

    Record the outcome and route for review

    A completed result routes to Landing; needs-input routes to Tower. The process-level session may be succeeded even when the result asks for input. The card shows the recorded result.

  10. Runner / finalization

    Attempt publication and remove the worktree

    The runner posts the result before its later branch-push step. If there are qualifying commits, it attempts to push the mission branch; a failed push is a separate event. Cleanup removes the worktree. Uncommitted artifacts inside it can be lost.

    A branch push is not a pull request, review, merge or deployment. There is no automatic draft-PR delivery in this path.

  11. Operator / acceptance

    Open the actual deliverable and decide

    Check that the report or code exists, is accessible, matches the requested scope and supports its claims. Confirm publication separately when relevant. Ask for correction or accept the result; move to Done only after acceptance.

Worktree policy needs an explicit decision. The Hangar runner uses disposable worktrees even at concurrency one. Your interactive swarm convention uses one shared checkout. Those are different execution modes. A persistent runner policy should say which mode applies to each repository; setting concurrency to one alone does not resolve the difference.

Source: launch/result actionspoller and worktree codethe real Swarm exercise.

07 / Operator playbook

Use it today as a supervised workflow.

Browser setup

Prepare the mission

  1. Open the dedicated production AI Hangar.
  2. Inspect Repositories. Match the intended realm, slug and allowed engine to the host mapping.
  3. Create an Agent mission. Choose one bounded objective and write what a satisfactory result must contain.
  4. Save draft first. Keep launch-on-drop off for initial supervised use.
Host setup

Establish readiness before polling

  1. Check all queued/running coding-card sessions for the account and other eligible hosts.
  2. Verify the local mapping and worktree policy, CLI login/model availability, environment command and required data access.
  3. Confirm where output will survive teardown and whether a branch may be pushed. The current runner can push committed mission work; prompt text alone is not a publication boundary.
  4. Only then start the selected runner and launch the intended mission.

Starting the runner is operationally significant: it may claim existing queued work immediately. The inspected host configuration allows up to four concurrent missions; the earlier Swarm test used a temporary concurrency-one runner. Do not interpret that historical test as the default configuration.

Where the existing Windows launcher lives

The foreground launcher is apps/kairos-worker/start-hangar-runner.bat. It expects installed workspace dependencies, an ignored runner.env.bat containing the Aeon connection settings, and a local repository mapping. It is not a Windows service or an autostart installation. A local health response is useful, but does not by itself prove model access, repo readiness or data connectivity. This guide does not start it.

For strict report-only/no-publication work, first ensure the chosen execution path actually enforces that scope. Ordinary Hangar finalization can push committed work. The 21 September research used a specific canonical-folder output workaround; it did not add a general retained-output channel.

While it runs and when it returns

  • Queued: look for an online runner and a compatible model/engine; do not repeatedly launch new attempts.
  • Running: inspect session events and recent heartbeat activity. Keep the host awake and available for supervised use.
  • Tower / needs input: read the questions. A successful process exit is not a completed objective.
  • Landing: open the actual artifact or inspect the branch/commit, then check tests and evidence. Review failed publication events as well as the result summary.
  • Done: your acceptance decision. Suggested follow-ups are proposals, not automatically authorized missions.

First practical acceptance exercise: inspect an existing mission and Repositories, save a deliberately incomplete draft and verify it stays idle. Then, after host/output preparation, run one short supervised mission and verify its delivered file after cleanup. This tests the user experience you asked for without treating queue transport as the final outcome.

09 / Recommended expansion sequence

Finish the delivery loop.
Then increase autonomy.

Prioritize work that makes one mission repeatable and inspectable. Scheduling more missions before setup, recovery and output delivery are dependable multiplies manual cleanup.

All phases below are proposed. They are ordered by dependencies and operator value, not delivery dates or effort estimates. Keep the existing Hangar and runner; introduce durable workflow machinery only where observed failure modes justify it.

01Make repository readiness visibleHighest immediate usability priority · keep the first profile narrow

Operator benefit: selecting Swarm tells you which machine can run it, which environment will be used and what is missing before you launch.

Build

  • A versioned repository execution profile: OS, host mapping, base revision policy, engine, environment invocation, required tools/skills and data capabilities.
  • A read-only “Check readiness” action on each host: checkout/ref exists, interpreter and dependencies resolve, CLI account offers the requested model, expected skills can be discovered. Test credentials without returning their values.
  • Host heartbeat and capability advertisement, including repository slugs; preview an eligible host and prevent unknown-repository claims.
  • Separate setup that changes files from the environment passed to the actual agent process. Expose clear effective values and cloud/local mismatches.

Start with Swarm and one supervised host. Add ARQ after that flow works; avoid a broad environment-management platform before the first useful result is reliable.

Exit proof: a new idle Swarm card shows the real host, base, interpreter, available model and discovered skills. An unavailable model or missing environment is reported before queueing. A bounded smoke mission uses those exact values.

Design precedents: GitHub setup workflowsDev Containersrunner routing.

02Deliver outputs before cleanupHighest outcome priority · complete before unattended use

Operator benefit: the card opens the report or reviewable code after the runner has stopped. You can tell whether publication succeeded.

Build

  • Capture declared artifacts before worktree deletion. Store a run-linked manifest with filenames, type, hash, source revision, authoring attempt, size and retention.
  • Make upload/capture completion a finalization gate. On failure, preserve recoverable output and show delivery pending or failed.
  • Add artifact links with appropriate access control to the result panel. Preserve logs and test evidence as well as the final report.
  • Record branch-push success separately from execution success. Enforce publication permission in the runner, so a report-only mission cannot push merely because it produced a commit.

Retain local or private storage where appropriate; the contract matters more than the storage vendor. An absolute filesystem path alone is insufficient for delivery from a phone or another machine.

Exit proof: after cleanup and with the source host offline, an authorized user opens the exact report from Hangar and verifies its manifest. A simulated upload or push failure remains visible and cannot be mistaken for delivered work.

Design precedent: workflow artifacts and retention. The existing receipt already identifies teardown loss; this phase closes it.

03Make runner loss recoverableReliability prerequisite · after durable output handling

Operator benefit: workstation sleep, restart or network loss produces a clear recoverable state instead of a mission appearing to run indefinitely.

Build

  • A supervised worker installation with explicit start, stop, drain and restart behavior; current process status and startup diagnostics.
  • Claim leases and a stale-session reconciler. Keep stable mission/attempt IDs and distinguish a lost worker from a failed objective.
  • Persist enough checkpoints to resume safe orchestration. Reconcile prior files, commits, results and publication before repeating side effects.
  • Bound retries and timeouts; make claim, result delivery and publication idempotent. Do not promise to resume a CLI’s private reasoning state.

A small database-backed state machine may be sufficient initially. Evaluate a workflow engine only if recovery paths outgrow that design; adopting Temporal is not itself the requirement.

Exit proof: interrupt the worker during execution and again during result delivery. Restart it and obtain one reconciled outcome, retained artifacts and no duplicate push. Test host sleep, expired lease and network interruption explicitly.

Design precedents: durable workflow historyidempotent activity retries.

04Make acceptance and publication explicitQuality prerequisite · bind review to the delivered revision

Operator benefit: “ready for review” means there is a specific delivered result to inspect, and “accepted” names who accepted what.

Build

  • Objective-specific completion requirements: a research evidence package, a plan document, or a code diff with meaningful checks.
  • Separate execution, delivery, review and human acceptance states. A new attempt invalidates any review tied to older outputs.
  • Optional independent review bound to immutable artifact hashes and commit revision. Preserve failed verdicts; never convert an executor’s self-report into independent review.
  • When authorized, create a draft PR and link it to the mission. Show branch push, PR creation, CI, acceptance, merge and deployment as separate outcomes.
  • Keep Done operator-owned, with an acceptance record and a clear request-correction path.

The existing Aeon OS exact-PASS harness is useful verification machinery. Turn its lessons into product contracts selectively; ordinary missions do not currently inherit that gate.

Exit proof: a reviewer inspects the exact preserved result; an edited artifact makes its prior review stale. A successful process with inadequate content stays unaccepted. A permitted code mission returns a draft PR with checks, without self-merging.

Design precedent: GitHub Copilot review boundaries. Current local basis: independent-review harness.

05Schedule bounded, dependency-aware workScale only after readiness, delivery and recovery pass

Operator benefit: recurring work and a batch of objectives run under known limits, with missed runs and blockers visible.

Build

  • A scheduler that creates durable mission intent with timezone, overlap/missed-run policy, pause, expiry and deduplication.
  • Priority and dependency-aware routing over repository-capable hosts. Distinguish mission concurrency from specialist concurrency within a mission.
  • Repository write ownership or explicit worktree policy, per-account limits, and clear behavior for exhausted model entitlement.
  • Bounded plan-then-execute or specialist assignments as recorded tasks within an objective. Keep suggested follow-ups as proposals until authorized.

Start with a scheduled read-only mission and a supervised batch. Time-based initiation should not silently grant new data, publication or trading permissions.

Exit proof: a scheduled mission survives an offline host without duplication; the UI reports late, missed or retried work. A five-objective batch respects dependencies and write isolation, and all outputs remain retrievable.

Design precedents: schedule limitationscapability routingsafe retries.

06Close the knowledge and decision loopOriginal Agent OS ambition · build on accepted outcomes

Operator benefit: your next session or morning view presents accepted findings, blockers and decisions, without forcing you to reconstruct terminal history.

Build

  • An inbox of delivered results, open questions, failed runs and decisions requiring you.
  • An explicit accepted-research ingestion path into the appropriate knowledge corpus, preserving provenance, as-of dates and review state.
  • Authorized summaries and references into Kairos; keep candidate reports distinct from accepted knowledge.
  • A replaceable, bounded coordinator that resumes from stored state and proposes next work rather than relying on an indefinite chat session.

This phase follows the original Aeon OS operating model; it is a product recommendation, not a claim established by the external workflow systems.

Exit proof: after five objectives, one view lets you open each accepted outcome, answer blockers and see why proposed next work matters. Replacing the coordinator session loses no recorded decisions or delivery references.

Product basis: Aeon OS outcome, responsibilities and five workstreams.

11 / Practical answers

The questions that matter at launch.

Does selecting Swarm automatically activate its Python environment?

No. The host must provide the tools/environment, and the mission should use an explicit command such as hatch run swarm_env_312:…. The repository UI does not currently bind a verified environment profile to the agent process. An activation in the separate setup shell does not carry over.

Does adding a Git URL clone the repository?

No. The poll worker resolves the slug to an existing host-local checkout. It does not fetch the cloud registry’s Git URL to create that checkout. Registering the repository and installing/mapping it on a host are separate operations.

Can it use ARQ as well as Swarm?

The current local mapping includes arq and the checkout exists. That proves configuration only. No ARQ execution was performed for this guide, and ARQ does not currently expose the same project skill directories found in Swarm. Confirm its runtime, environment and instructions before a first mission.

Will a mission see changes I have not committed?

Not automatically. The worker creates a Git worktree from its configured base/mission branch. Uncommitted changes in the original checkout do not become that worktree’s tracked content. Explicit local links/copies can expose selected files, so the effective workspace needs inspection.

Can I launch from a different computer or my phone?

You can queue through hosted Aeon when authenticated. Execution still requires an eligible authenticated runner. Opening the site remotely does not start your workstation or wake it from sleep. This guide verified no local listener on known runner ports at its dated inspection, not the absence of every possible remote host.

What if the runner stops halfway through?

There is no complete stale-session recovery loop. A claimed session may remain running after host loss. Treat a stale heartbeat as an investigation signal, preserve existing work, and reconcile before starting a duplicate attempt. A foreground launcher is not an always-on service.

Does Landing mean reviewed or accepted?

No. It is automatic routing of a completed result for your review. The exact-PASS different-model gate belongs to the separate Aeon OS verification harness; ordinary mission completion does not automatically run it.

Where are reports and code delivered?

The result panel records paths and branch/commit information. Committed mission work can be pushed by the runner; general hosted reports and automatic draft PR creation are unfinished. Uncommitted files in the disposable worktree can be removed at cleanup, so output preservation must be planned before launch.

Do priority, dependencies or suggested next tasks trigger work?

They do not constitute the planned autonomous scheduler. Current launches are explicit or use the one-shot, opted-in drop trigger. Claims are oldest-first within the current matching rules. Suggested tasks remain proposals.

Is the selected model definitely available?

The UI offers a static catalog, not live account entitlement. The inspected Copilot account listed Sonnet 5 on 22 September but did not list the configured Opus 5 default or Sol reviewer. Check the actual account again before dispatch; model availability is a time-sensitive observation.
