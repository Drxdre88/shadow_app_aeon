# Recon: Session Claim Ownership

Unique marker: AEON_OS_E2E_2026-09-11T12-17-25-014Z-1a3691_01

Scope: `apps/web/src/lib/data/sessions.ts` (claim/dispatch/result lifecycle) and its
focused tests in `apps/web/src/lib/data/__tests__/sessions-claim.test.ts`.

## Findings

1. **Claim ownership is enforced by a single-transaction SELECT-FOR-UPDATE-then-UPDATE, scoped to the calling user, card-linked rows only, with row-skip locking for concurrent runners.**
   Observed: `apps/web/src/lib/data/sessions.ts:150` (`claimNextSession`) opens a `db.transaction` whose SELECT filters on `eq(agentSessions.userId, userId)`, `eq(agentSessions.status, 'queued')`, and `isNotNull(agentSessions.taskId)` (`apps/web/src/lib/data/sessions.ts:162`), then locks the candidate with `.for('update', { skipLocked: true })` (`apps/web/src/lib/data/sessions.ts:167`) before the UPDATE flips it to `running` and stamps `claimedBy`/`claimedAt`. The `taskId IS NOT NULL` predicate excludes non-card session rows (e.g. chat/dialogue threads) from ever being claimed by a runner. This is corroborated by the test suite: `apps/web/src/lib/data/__tests__/sessions-claim.test.ts:120` asserts `forArgs` equals `['update', { skipLocked: true }]`, and the comment at `apps/web/src/lib/data/__tests__/sessions-claim.test.ts:5` states the predicate is "user-scoped, card-linked only... queued only, engine-narrowed" — confirming this is treated as a security boundary, not a mere filter.

2. **The claim's engine filter is caller-supplied and defaults to all three claimable engines, but is not validated against the session's original `engine` column beyond inclusion in the caller's list.**
   Observed: `apps/web/src/lib/data/sessions.ts:150` signature takes `engines: HangarAgent[] = CLAIMABLE_ENGINES` (declared at `apps/web/src/lib/data/sessions.ts:16` as `['claude', 'codex', 'copilot']`) and applies it via `inArray(agentSessions.engine, engines)` inside the same WHERE clause as the ownership/status/taskId checks. Test `apps/web/src/lib/data/__tests__/sessions-claim.test.ts:129` ("narrows the claim to the engines the runner asked for") confirms a runner passing `['codex']` only matches `codex`-engine rows and the bound params exclude `'claude'`. Inference: a runner process is trusted to pass the correct engine list for itself — the function does not independently verify the caller *is* that engine type; that verification (if any) would need to happen at whatever authenticates the runner call before reaching this data-layer function, which is out of scope here.

3. **Result posting (`recordSessionResult`) uses a WHERE-clause terminal-status guard (not a prior read) to make "settle a session" idempotent under racing posts, and only the winner touches the linked board card.**
   Observed: `apps/web/src/lib/data/sessions.ts:262` — the transactional UPDATE's WHERE includes `notInArray(agentSessions.status, TERMINAL_STATUSES)` (terminal set defined at `apps/web/src/lib/data/sessions.ts:14` as `['succeeded', 'failed', 'killed', 'timeout']`), so a session already in one of those statuses matches zero rows on a second/late call and the function returns `{ session, task: null }` without invoking `updateTask`/touching the card. This is exercised directly by `apps/web/src/lib/data/__tests__/sessions-claim.test.ts:191` ("carries the terminal-status guard in the UPDATE, not in a prior read"), which compiles the captured WHERE SQL and asserts it contains `"agent_sessions"."status" not in ($2, $3, $4, $5)` with params `['succeeded','failed','killed','timeout']`. A companion parameterized test near `apps/web/src/lib/data/__tests__/sessions-claim.test.ts:177` ("refuses to re-apply a result to a %s session") confirms this for every terminal status individually.

4. **Claim ownership at the *insert* boundary (one live mission per card) is enforced by a partial DB unique index surfaced through error-message sniffing, not by an application-level check-then-insert.**
   Observed: `apps/web/src/lib/data/sessions.ts:36` defines `ONE_LIVE_PER_TASK_IDX = 'agent_sessions_one_live_per_task_idx'`, and the `LiveMissionExistsError` class is declared at `apps/web/src/lib/data/sessions.ts:29` just above `createAgentSession`, whose catch block inspects the thrown Postgres error's message for that index name to translate it into `LiveMissionExistsError`. The inline comment above the catch states this index is "the authoritative one-live-mission-per-card guard" covering both the app's own spawn path and other REST/MCP spawn surfaces "which never ran that check." Inference: the actual index definition/migration (referenced as "migration 0033" in the comment) was not opened in this recon pass, so its exact predicate/columns are not independently observed here — only the string constant and the code's reliance on it.
