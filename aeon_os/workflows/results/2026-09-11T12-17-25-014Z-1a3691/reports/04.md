Scope: `apps/web/src/components/board/MissionEditorModal.tsx` and its component tests.

## Findings

1. **Auto-run seeds from saved metadata, not a hardcoded false.** `draftFromMetadata` sets `autoRun: h.autoRun === true` from the card's saved `metadata.hangar` (observed code, apps/web/src/components/board/MissionEditorModal.tsx:47). The docblock immediately above the component states this is an "Owner directive: auto-run always re-defaults to OFF for fresh missions" (observed code, apps/web/src/components/board/MissionEditorModal.tsx:44-47 comment block preceding line 47). For a task with no prior `hangar` metadata this yields OFF; whether any code path resets an *existing* saved `autoRun: true` back to OFF was not observed and is inference only.

2. **The draft-seeding effect deliberately excludes `task` from its dependency array to avoid clobbering in-progress typing.** Observed at apps/web/src/components/board/MissionEditorModal.tsx:74-76 ("Draft is seeded once per open; live task edits elsewhere must not clobber in-progress typing" plus `eslint-disable-next-line react-hooks/exhaustive-deps`), with the effect's dependency array being `[missionEditorTaskId]` alone. Consequence (inference from the comment and dependency array, not covered by any observed test): if `task.metadata` changes elsewhere while the modal is open (e.g. a real-time update), the open draft will not pick that change up.

3. **No component test file exists for `MissionEditorModal`.** A repository-wide glob for `**/MissionEditorModal*.test.*` returned zero matches (observed absence). The only other repository reference to the component is its consumer: import at apps/web/src/components/board/TaskBoard.tsx:8 and render at apps/web/src/components/board/TaskBoard.tsx:478. This leaves the save/launch busy-state machine and the `canSave` gate at apps/web/src/components/board/MissionEditorModal.tsx:97 (`draft.repo.trim().length > 0 && draft.instruction.trim().length > 0 && busy === null`) without automated coverage (observed absence of tests).

4. **`persist()` performs a direct, non-debounced server write specifically so a follow-up launch reads the just-saved mission rather than a stale queued value.** The comment at apps/web/src/components/board/MissionEditorModal.tsx:101 ("Direct server write (not the debounced queue): a follow-up launch must read the saved mission, not a stale card") documents this intent (observed code). `persist()` calls `saveCardMission(projectId, task.id, {...})`, whose export is defined at apps/web/src/lib/actions/hangar.ts:193 (observed). `handleLaunch` awaits `persist()` before calling `spawnSessionFromCard(projectId, task.id)`, whose export is defined at apps/web/src/lib/actions/hangar.ts:105 (observed), consistent with the ordering guarantee described in the comment.

5. **Repo/engine compatibility is enforced client-side by disabling (not hiding) disallowed engine buttons.** `engineAllowed(engine)` in apps/web/src/components/board/MissionEditorModal.tsx returns `true` whenever `selectedRepo` is null or `selectedRepo.allowedEngines.length === 0`, otherwise checks `selectedRepo.allowedEngines.includes(engine)` (observed code, function definition following the `selectedRepo` memo). Disallowed engine buttons receive `disabled` plus the `opacity-40 cursor-not-allowed` class rather than being removed from the list. The repo list itself is fetched via `listProjectHangarRepos(projectId)`, exported at apps/web/src/lib/actions/hangar.ts:174 (observed), inside a `useEffect` keyed on `[missionEditorTaskId, projectId]`. Whether `saveCardMission` or `spawnSessionFromCard` re-validate the engine/repo allowlist server-side was not checked in this bounded scope (inference — flagged as a possible TOCTOU-style validation gap if the server layer relies solely on client gating).
