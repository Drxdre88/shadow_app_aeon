# Recon: Terminal Result Retries (kairos-worker)

Unique marker: AEON_OS_E2E_2026-09-11T12-17-25-014Z-1a3691_09

Scope: `apps/kairos-worker/src/callback.ts` and the poller's mission-finalization
path (`apps/kairos-worker/src/poller.ts`).

## Findings (observed code)

1. **Terminal writes use a fixed 3-step backoff, distinct from the batch-event
   retry.** `apps/kairos-worker/src/callback.ts:14` defines
   `RETRY_DELAYS_MS = [5_000, 15_000, 45_000]`, consumed by `withRetry`
   (`apps/kairos-worker/src/callback.ts:184`), which loops over the array,
   re-invoking the caller's `attempt()` and sleeping between tries via
   `apps/kairos-worker/src/callback.ts:189`. This is a longer window (up to
   ~65s across 4 attempts) reserved for the two writes the finalize path
   treats as must-land: the result event and the final status PATCH — a
   comment at `apps/kairos-worker/src/callback.ts:12` states this is because
   "a chatty stream can spend that budget right before the terminal post".
   This differs from `postEventsBatch`'s single 3s retry
   (`apps/kairos-worker/src/callback.ts:139`), which is scoped for in-flight
   telemetry chunks, not terminal results.

2. **Retry eligibility is status-code gated, not blanket.** `retriable()` at
   `apps/kairos-worker/src/callback.ts:174-175` only returns true for
   `status === 0` (network/timeout), `408`, `429`, or `>= 500`. `withRetry`
   (`apps/kairos-worker/src/callback.ts:184-196`) checks `!retriable(res.status)`
   before each additional attempt, so a 4xx that isn't 408/429 (e.g. a schema
   validation 400) is never retried and fails immediately — consistent with
   the comment at `apps/kairos-worker/src/callback.ts:171-172` ("a 4xx that
   means 'this payload is wrong' is not [worth another go]").

3. **The finalization path runs two independent `withRetry` calls for the two
   terminal writes, and does not abort the second if the first indicates a
   rejection.** `apps/kairos-worker/src/poller.ts:511-512` retries posting the
   `result` event (`kind: 'result'`) and captures its ack; then, regardless of
   whether that ack indicated an Aeon-side rejection,
   `apps/kairos-worker/src/poller.ts:526` unconditionally runs a second,
   separate `withRetry('final status', ...)` call to PATCH the session's
   terminal status. The two writes are not part of one retry unit — a result
   event that lands only after retries, or is ultimately rejected, does not
   block or change the mechanics of the following status-PATCH retry loop
   (though the *value* it patches is affected, per finding 4).

4. **Envelope rejection is distinguished from other outcomes before deciding
   final status.** `envelopeRejection()` at
   `apps/kairos-worker/src/poller.ts:472-475` inspects the `ResultAck`
   returned by the retried result-event POST and only treats it as a
   rejection when `resultProcessed === false` **and** `resultError` is a
   string — the adjacent comment (`apps/kairos-worker/src/poller.ts:463-465`)
   notes `resultProcessed` can also read `false` for "a replay or an unlinked
   session", which is not an error. `apps/kairos-worker/src/poller.ts:524`
   feeds this `rejection` boolean into `decideFinalStatus(...)`, whose result
   is what the retried `patchSession` call
   (`apps/kairos-worker/src/poller.ts:526`) ultimately writes — so a rejected
   envelope can still change the *status* value being retried/written, even
   though the retry mechanics themselves (finding 3) are unaffected.

## Inference (not directly observed in this scope)

- The actual `decideFinalStatus` implementation was not opened in this recon
  pass (only its call site at `apps/kairos-worker/src/poller.ts:524` and the
  `envelopeRejection` helper it consumes were inspected), so the exact mapping
  from `(reported, wasKilled, rejection)` to a final status string is inferred
  from naming and call-site usage, not confirmed by reading its body.
- Whether the Aeon server-side `/api/v1/sessions/:id/events` and
  `/api/v1/sessions/:id` routes themselves apply any additional retry-safe
  idempotency (e.g. de-duplicating a result event replayed by `withRetry`) was
  out of scope for this pass and was not verified.
