# Auto-drop launch behavior — recon report

Unique marker: AEON_OS_E2E_2026-09-11T12-17-25-014Z-1a3691_05

Scope: `apps/web/src/components/board/autoRun.ts` (pure predicate) and the
`useBoardDnD` auto-run wiring/tests (`apps/web/src/components/board/useBoardDnD.ts`,
`apps/web/src/components/board/__tests__/useBoardDnD-autoRun.test.tsx`).

## Findings

1. **Observed.** The launch predicate fails closed by design: `shouldAutoRunOnDrop`
   requires `config.enabled` and `config.triggerColumnId` to be set, the drop's
   `toColumnId` to equal the trigger column, a non-null `fromColumnId` that differs
   from `toColumnId` (so same-column reorders never qualify), a "complete" mission
   payload per `isLaunchableMission`, and the card's own `metadata.hangar.autoRun`
   flag to be strictly `=== true`. See
   `apps/web/src/components/board/autoRun.ts:44` through
   `apps/web/src/components/board/autoRun.ts:51`.

2. **Observed.** A missing/unknown origin column (`fromColumnId` falsy) is treated
   as an unprovable drop and rejected rather than assumed safe — an explicit
   "fail closed" comment documents this tradeoff (accepting false negatives over
   a wrongly-armed real agent launch) at
   `apps/web/src/components/board/autoRun.ts:45`-`apps/web/src/components/board/autoRun.ts:49`.

3. **Observed.** In the hook, a no-op drop (same column and same `orderIndex`)
   short-circuits with an early `return` at
   `apps/web/src/components/board/useBoardDnD.ts:211`, which happens *before* the
   auto-run arming block runs, so a no-op reorder can never reach
   `shouldAutoRunOnDrop` at all — this is a wiring-level guard distinct from the
   predicate's own `fromColumnId === toColumnId` check.

4. **Observed.** Arming is additionally gated on board scope: even when the
   predicate would return true, `useBoardDnD.ts` requires
   `hangarState.projectId === activeTask.projectId` before calling
   `shouldAutoRunOnDrop`, so an Auto-AI config left over from a different board
   cannot arm drops on the current one. See
   `apps/web/src/components/board/useBoardDnD.ts:221`-`apps/web/src/components/board/useBoardDnD.ts:222`.

5. **Observed.** The actual launch is never performed inside the drag handler.
   The hook only attaches an intent object (`{ autoRunTaskId, armedAt: Date.now() }`)
   as the third argument to the `onTaskMove` callback when armed, or `undefined`
   otherwise — the mutation and the "should we launch" decision are deliberately
   decoupled so a rolled-back move can't leave a live agent running. See
   `apps/web/src/components/board/useBoardDnD.ts:228`.

6. **Observed (test-asserted).** The test suite explicitly locks in that the hook
   exposes no launch capability of its own — `Object.keys(hook.result.current)`
   is asserted to not contain `launchMission` — corroborating finding 5 that
   launching is entirely the caller's responsibility. See
   `apps/web/src/components/board/__tests__/useBoardDnD-autoRun.test.tsx:128`.

7. **Observed (test-asserted).** A board-scope mismatch is directly covered by a
   dedicated test that sets `useHangarUiStore` to a different `projectId` than
   the dragged task's own board and asserts no launch intent is produced,
   corroborating finding 4. See
   `apps/web/src/components/board/__tests__/useBoardDnD-autoRun.test.tsx:158`-`apps/web/src/components/board/__tests__/useBoardDnD-autoRun.test.tsx:159`.

8. **Inference.** Because arming depends on `activeTask.projectId` and
   `hangarState.projectId` both being read at drop time (not at drag-start time),
   a board switch that occurs mid-drag (if ever possible in the UI) could change
   which config gates the same drag; no test in
   `apps/web/src/components/board/__tests__/useBoardDnD-autoRun.test.tsx` exercises
   a board switch mid-drag (only a config already set to another board before
   the drag starts), so this remains untested behavior rather than an observed
   guarantee.

## Distinguishing observed vs. inferred

Findings 1–7 are directly observed from source and test code as cited above.
Finding 8 is an inference about untested edge-case behavior, not a verified
runtime observation.
