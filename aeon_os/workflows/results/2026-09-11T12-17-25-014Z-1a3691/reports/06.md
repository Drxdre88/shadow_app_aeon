# Mission Cancellation Recon — AEON_OS_E2E_2026-09-11T12-17-25-014Z-1a3691_06

Marker: AEON_OS_E2E_2026-09-11T12-17-25-014Z-1a3691_06

Scope: session kill routes/actions and worker cancellation paths. Repository-only
research; no source files were modified.

## Findings (observed code)

1. **REST kill endpoint always marks the session killed, even if the worker is
   unreachable.** `apps/web/src/app/api/v1/sessions/[id]/kill/route.ts:24-37`
   attempts `POST {KAIROS_WORKER_URL}/kill/{session.id}` inside a try/catch that
   swallows any fetch error (`workerAck = false` on failure), then
   unconditionally calls `updateAgentSessionStatus(id, auth.id, { status: 'killed', endedAt: new Date() })`
   regardless of `workerAck`. The route's own comment
   (`apps/web/src/app/api/v1/sessions/[id]/kill/route.ts:8-10`) states this is
   intentional: "updates the row to status='killed' regardless so the UI
   reflects the operator's intent even when the worker is unreachable."

2. **A server action duplicates the same kill logic outside the REST/MCP
   parity surface.** `apps/web/src/lib/actions/sessions.ts:114` defines
   `killSessionAction(id)`, which independently performs the same
   `fetch(\`${workerUrl}/kill/${session.id}\`)` call
   (`apps/web/src/lib/actions/sessions.ts:123`) and the same
   `updateAgentSessionStatus(id, userId, { status: 'killed', endedAt: new Date() })`
   fallback (`apps/web/src/lib/actions/sessions.ts:133`). This is a second,
   separately maintained implementation of the same cancellation behavior
   rather than a shared helper called from both the REST route and the
   action.

3. **The worker process exposes an inbound HTTP `/kill/:id` route that calls
   into the in-process session registry.** `apps/kairos-worker/src/index.ts:104-107`
   matches `POST /kill/<sessionId>` and calls `killSession(sessionId)` from
   `apps/kairos-worker/src/spawner.ts`, returning HTTP 200 if a live session
   was found and killed, or 404 otherwise.

4. **Worker-side `killSession` uses a platform-specific tree kill with a
   fallback signal.** `apps/kairos-worker/src/spawner.ts:459-474` sets
   `session.killed = true` (line 462) so the exit handler reports status
   `'killed'` however the child actually dies, then on Windows shells out to
   `spawnSync('taskkill', ['/PID', String(pid), '/T', '/F'], ...)`
   (`apps/kairos-worker/src/spawner.ts:469`) to kill the whole process tree,
   falling back to `session.child.kill('SIGTERM')` if `taskkill` did not exit
   0 (`apps/kairos-worker/src/spawner.ts:470`) or on non-Windows platforms
   (`apps/kairos-worker/src/spawner.ts:474`).

5. **A second, independent cancellation path exists via status polling, for
   when the worker has no inbound port reachable by the web app.**
   `apps/kairos-worker/src/poller.ts:622` documents this: "cooperative kill
   without an inbound port." The poller reads the session's remote status and,
   if it observes `readStatus(current.data) === 'killed'`
   (`apps/kairos-worker/src/poller.ts:641`), logs
   `"${sessionId} killed from Aeon — SIGTERM"` (`apps/kairos-worker/src/poller.ts:642`)
   and calls `killSession(sessionId)` locally — meaning a session can be
   cancelled by the web app flipping the DB row to `'killed'` even if the
   `/kill/:id` HTTP call to the worker never succeeds, as long as the worker's
   poll loop later observes that status.

6. **Internal poller `abort()` also invokes `killSession`, but for a distinct
   set of failure triggers, not operator-initiated cancellation.**
   `apps/kairos-worker/src/poller.ts:225-230` defines an `abort(message)`
   helper that, if the child process is still running, calls
   `killSession(session.id)` (`apps/kairos-worker/src/poller.ts:230`). This
   path is invoked for setup failures such as an unsupported engine
   (`apps/kairos-worker/src/poller.ts:248`), a repo missing from the repos
   file (`apps/kairos-worker/src/poller.ts:252`), a repo path that does not
   exist on the host (`apps/kairos-worker/src/poller.ts:255`), worktree
   preparation failure (`apps/kairos-worker/src/poller.ts:267`), or an
   `envSetupCmd` failure (`apps/kairos-worker/src/poller.ts:275`) — i.e.
   pre-launch validation failures reuse the same kill machinery as
   operator-initiated cancellation.

## Inference (not directly observed in this recon pass)

- Findings 1 and 2 (the REST route and the server action both independently
  reimplementing the worker-kill + status-update sequence) suggest the same
  duplication risk called out by this repo's documented MCP/REST parity
  invariant, but this recon did not search for or find an existing automated
  test analogous to `gantt-parity.test.ts` that guards kill-path parity
  between the action and the REST route; whether one exists elsewhere in the
  test suite was not verified.
- The "cooperative kill" path (finding 5) implies the worker's poll interval
  bounds the latency between an operator clicking kill in the UI and the
  underlying CLI process actually being signaled, in cases where the direct
  `/kill/:id` HTTP call fails; the exact poll interval was not located in this
  pass.
