# Flight Deck telemetry — stream-parser & timeline consumers

Marker: AEON_OS_E2E_2026-09-11T12-17-25-014Z-1a3691_08

Bounded scope: `apps/kairos-worker/src/stream-parser.ts` and its consumers
(`apps/kairos-worker/src/engines.ts`, `apps/kairos-worker/src/poller.ts`,
`apps/kairos-worker/src/spawner.ts`). All findings below are observed directly
in source unless explicitly marked "Inference".

## Findings

1. **Only the Claude engine gets typed telemetry; other engines fall back to raw
   text batching.** `apps/kairos-worker/src/engines.ts:33` declares
   `streamParser?: () => StreamParser` as optional on the `EngineAdapter`
   interface, and only the `claude` adapter wires it:
   `apps/kairos-worker/src/engines.ts:76` sets
   `streamParser: createClaudeStreamParser`. The consumer,
   `apps/kairos-worker/src/poller.ts:294`
   (`const parser = engine.streamParser?.() ?? null`), passes `undefined` for
   any engine without one. In `apps/kairos-worker/src/spawner.ts:354`
   (`child.stdout` handler) and `apps/kairos-worker/src/spawner.ts:276`
   (`pendingEvents.push({ kind: 'message', payload: { stream: 'stdout', text: chunk } })`),
   the fallback path posts one coarse `message` event per stdout chunk instead
   of the typed `tool_use`/`tool_result`/`thinking`/`usage` events the parser
   produces — so copilot/codex missions render as raw text soup on the Flight
   Deck timeline while claude missions render structured events (comment at
   `apps/kairos-worker/src/engines.ts:31-33` confirms this is the documented
   intent, not an oversight).

2. **A stalled partial line (e.g. a spinner using bare `\r`) is bounded by a
   1MB tail cap, not dropped silently.** `apps/kairos-worker/src/stream-parser.ts:56`
   defines `const TAIL_CAP = 1_000_000` with the accompanying comment
   (`apps/kairos-worker/src/stream-parser.ts:52-55`) explaining that a lone CR
   is not a line separator, so a CLI progress spinner would otherwise grow the
   partial-line buffer unbounded (60KB observed in practice per the comment).
   The cap is enforced in `feed()` at
   `apps/kairos-worker/src/stream-parser.ts:379-382`
   (`if (tail.length > TAIL_CAP) { raw += \`${tail}\n\`; tail = '' }`), which
   flushes the buffer back to the caller as raw text and resets it rather than
   losing data.

3. **Tool names are truncated to 80 characters before being stored, specifically
   to protect the events table's column width.** In
   `apps/kairos-worker/src/stream-parser.ts:271-273`
   (inside `mapAssistantLine`), `const name = b.name.slice(0, 80)` is applied
   to every `tool_use` block, with the comment "The server's toolName column
   caps at 80; a long MCP tool name must not 400 the events beside it." This is
   an observed defensive truncation tightly coupled to a downstream DB schema
   constraint (the column width itself is outside this file's scope and not
   verified here — inference only that it lives in the server's events table).

4. **Usage events are deduplicated per API request_id, not per stream line, to
   correctly account for interleaved parallel subagents.** `ClaudeCtx` at
   `apps/kairos-worker/src/stream-parser.ts:200-211` keys `pendingUsage` and
   `flushedUsage` by `request_id` rather than a single pending slot, with the
   comment explaining that parallel subagents interleave their usage lines
   (e.g. request A, B, A) — `trackUsage()`
   (`apps/kairos-worker/src/stream-parser.ts:229-235`) only records the latest
   snapshot per request, and `flushPendingUsage()`
   (`apps/kairos-worker/src/stream-parser.ts:215-222`) drains them in
   first-seen order so each request contributes exactly one `usage` event to
   the timeline instead of double-counting.

5. **The parser is never allowed to crash mission ingestion: both `feed()` and
   `flush()` calls in the consumer are wrapped in try/catch that degrade to raw
   text.** `apps/kairos-worker/src/spawner.ts:354`
   (`const out = opts.parser.feed(text)`) and
   `apps/kairos-worker/src/spawner.ts:333`
   (`const out = opts.parser.flush()`) are both inside `try { … } catch (err) {
   parserThrew(...); appendRaw(text) }` blocks
   (`apps/kairos-worker/src/spawner.ts:336-342` and
   `apps/kairos-worker/src/spawner.ts:356-360`). The comment at
   `apps/kairos-worker/src/spawner.ts:338-340` notes the terminal result
   envelope is read from captured stdout independent of the parser, so a
   parser exception on `flush()` loses only the still-buffered typed events,
   not the mission's final outcome.

6. **jsonb-unsafe bytes (NUL and lone UTF-16 surrogates) are stripped/replaced
   before any tool payload reaches the DB layer, because Postgres jsonb
   rejects both.** `apps/kairos-worker/src/stream-parser.ts:63-68` defines
   `JSONB_UNSAFE` (`\u0000`) and `LONE_SURROGATE` regexes with comments
   explaining Postgres jsonb refuses `\u0000` escapes and unpaired surrogate
   escapes; `jsonbSafeString()` at
   `apps/kairos-worker/src/stream-parser.ts:69-71` applies both replacements,
   and it is used both in the per-field `cap()` helper
   (`apps/kairos-worker/src/stream-parser.ts:157-166`) and in the deep-walk
   `sanitizeJsonbDeep()` (`apps/kairos-worker/src/stream-parser.ts:139-149`)
   which the comment there ties specifically to the terminal result envelope
   being "the one payload written to jsonb without passing through cap()".

## Observed vs. inference

- Findings 1–6 are all directly observed in the cited source lines and their
  adjacent comments.
- The claim in Finding 3 about *where* the server's 80-char `toolName` column
  is defined is inference — only the enforcement site in the worker
  (`apps/kairos-worker/src/stream-parser.ts:271-273`) was inspected; the
  server-side schema itself was outside this mission's bounded scope.
