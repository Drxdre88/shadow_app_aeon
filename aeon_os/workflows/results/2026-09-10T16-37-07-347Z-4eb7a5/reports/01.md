# Session Claim Ownership — Recon Report

AEON_OS_E2E_2026-09-10T16-37-07-347Z-4eb7a5_01

Scope: `apps/web/src/lib/data/sessions.ts` and `apps/web/src/lib/data/__tests__/sessions-claim.test.ts`.

## Findings

1. **Observed.** `claimNextSession` scopes its candidate `SELECT` to `eq(agentSessions.userId, userId)` AND `eq(agentSessions.status, 'queued')` AND `isNotNull(agentSessions.taskId)` AND `inArray(agentSessions.engine, engines)`, ordered by `asc(agentSessions.spawnedAt)` with `.for('update', { skipLocked: true })` (`apps/web/src/lib/data/sessions.ts:148-160`). The `isNotNull(taskId)` predicate is the guard that keeps kairos-chat/dialogue rows (which share the `agent_sessions` table but have no `taskId`) from ever being claimed by a runner, per the comment at `apps/web/src/lib/data/sessions.ts:139-146`.

2. **Observed.** The claim is a two-step SELECT-then-UPDATE inside a single `db.transaction`, and the follow-up `UPDATE` is keyed only on `eq(agentSessions.id, candidate.id)` — not re-checked against `userId`/`status` (`apps/web/src/lib/data/sessions.ts:162-175`). Row-level ownership safety for the claim therefore depends entirely on `SKIP LOCKED` plus the transaction boundary preventing a second candidate row from being selected concurrently, not on a defense-in-depth WHERE clause on the UPDATE. This is corroborated by the test `'locks the candidate row with SKIP LOCKED so runners can poll concurrently'`, which asserts `captures[0].forArgs` equals `['update', { skipLocked: true }]` (`apps/web/src/lib/data/__tests__/sessions-claim.test.ts:114-121`).

3. **Observed.** The test suite verifies the WHERE clause compiles to `"agent_sessions"."user_id" = $1` and `"agent_sessions"."status" = $2` with `params[0] === USER_ID`, and separately asserts `params` never contains `OTHER_USER`, i.e. the claim query is user-scoped by construction and the test would fail if another user's id leaked into the bound parameters (`apps/web/src/lib/data/__tests__/sessions-claim.test.ts:100-111`). The default-engines test additionally pins the engine allow-list ordering to `['claude', 'codex', 'copilot']` (`apps/web/src/lib/data/__tests__/sessions-claim.test.ts:135-141`), matching the `CLAIMABLE_ENGINES` constant (`apps/web/src/lib/data/sessions.ts:19`).

4. **Observed.** `claimNextSession` returns `null` on an empty queue without issuing any UPDATE — the test `'returns null on an empty queue without touching any row'` asserts `captures` has length 1 (only the SELECT capture) (`apps/web/src/lib/data/__tests__/sessions-claim.test.ts:143-149`), confirming no UPDATE call is made when no candidate row is found (`apps/web/src/lib/data/sessions.ts:161`, the `if (!candidate) return null` short-circuit).

5. **Inference.** Because the transaction only performs the row lock/select and the update — the code comment at `apps/web/src/lib/data/sessions.ts:141-143` states "the Neon pool times an acquire out at 8s, so a transaction that waits on anything else can strand the pool" — the ownership guarantee ("a runner must never execute another user's prompt") is likely intentionally kept cheap/fast rather than layered with a second ownership check in the UPDATE, trading defense-in-depth for latency safety under Neon's connection-pool constraints. This is inferred from the comment's stated rationale, not directly asserted by a test.

## Distinguishing observed vs. inferred

Findings 1–4 are directly observed from source and test assertions. Finding 5 is an inference about design intent drawn from the in-code comment, not a directly tested guarantee.
