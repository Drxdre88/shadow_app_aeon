# Session claim ownership — recon

Unique marker: AEON_OS_E2E_2026-09-16T14-58-19-989Z-0f2824_01

Scope: `apps/web/src/lib/data/sessions.ts` (claim/dispatch lifecycle) and its
focused tests in `apps/web/src/lib/data/__tests__/sessions-claim.test.ts`.

## Findings (VERIFIED — read directly from source)

1. **Claim is transactional, row-locked, and scoped to caller + card-linked + queued rows only.**
   `claimNextSession` (apps/web/src/lib/data/sessions.ts:174) runs inside `db.transaction`
   and selects a candidate with `eq(agentSessions.userId, userId)`,
   `eq(agentSessions.status, 'queued')`, `isNotNull(agentSessions.taskId)`
   (apps/web/src/lib/data/sessions.ts:186), and `inArray(agentSessions.engine, engines)`, then
   locks it with `.for('update', { skipLocked: true })` (apps/web/src/lib/data/sessions.ts:191).
   The `taskId IS NOT NULL` predicate is called out in the preceding comment
   (apps/web/src/lib/data/sessions.ts:161-166) as mandatory because kairos-chat/dialogue
   rows share the same table and must never be claimable as missions. This is confirmed by
   the test `claims a queued, card-linked session for the calling user only`
   (apps/web/src/lib/data/__tests__/sessions-claim.test.ts:88), which asserts the compiled WHERE
   SQL contains `"agent_sessions"."task_id" is not null` and that bound params never include
   another user's id.

2. **SKIP LOCKED enables concurrent runner polling without blocking; the claim update stamps ownership atomically in the same transaction.**
   Test `locks the candidate row with SKIP LOCKED so runners can poll concurrently`
   (apps/web/src/lib/data/__tests__/sessions-claim.test.ts:120) asserts
   `captures[0].forArgs` equals `['update', { skipLocked: true }]`. The subsequent update inside
   the same transaction (apps/web/src/lib/data/sessions.ts:195-206) sets
   `status: 'running', claimedBy: workerId, claimedAt, lastHeartbeatAt, startedAt, updatedAt`, and
   test `stamps the claim on the row it flips to running`
   (apps/web/src/lib/data/__tests__/sessions-claim.test.ts:151) confirms the second capture's
   `set` matches `{ status: 'running', claimedBy: WORKER }`. The engine allow-list defaults to
   `CLAIMABLE_ENGINES = ['claude', 'codex', 'copilot']` (apps/web/src/lib/data/sessions.ts:14),
   verified by `defaults to every claimable engine`
   (apps/web/src/lib/data/__tests__/sessions-claim.test.ts:135-142).

3. **Result posting is idempotent via a WHERE-clause guard, not a prior read, closing a race between duplicate result posts.**
   `recordSessionResult` (apps/web/src/lib/data/sessions.ts:249) reads the session first but the
   authoritative terminal check is embedded in the transactional UPDATE's WHERE clause via
   `notInArray(agentSessions.status, TERMINAL_STATUSES)` (apps/web/src/lib/data/sessions.ts:286),
   with `TERMINAL_STATUSES = ['succeeded', 'failed', 'killed', 'timeout']`
   (apps/web/src/lib/data/sessions.ts:16). The inline comment above the update
   (apps/web/src/lib/data/sessions.ts:277-281) states this deliberately: "two result posts racing
   on the same session would both pass a read-then-write check ... Postgres settles it — the
   loser updates zero rows." This is exercised by
   `carries the terminal-status guard in the UPDATE, not in a prior read`
   (apps/web/src/lib/data/__tests__/sessions-claim.test.ts:191), which compiles the captured WHERE
   clause and asserts `"agent_sessions"."status" not in ($2, $3, $4, $5)` with params
   `[SESSION_ID, 'succeeded', 'failed', 'killed', 'timeout']`, and by
   `processes the card exactly once when two result posts race`
   (apps/web/src/lib/data/__tests__/sessions-claim.test.ts:203), which simulates a winner (card
   updated, `touchProject` called once) followed by a loser whose guarded UPDATE matches zero
   rows and whose card-write/`touchProject` call counts stay unchanged.

4. **Session-launch dedup (`createAgentSession`/`isOneLivePerTaskViolation`) is a separate guard from claim, defending a partial unique index and walking driver error causes.**
   `isOneLivePerTaskViolation` (apps/web/src/lib/data/sessions.ts:46-59) walks up to
   `MAX_CAUSE_DEPTH = 5` (apps/web/src/lib/data/sessions.ts:43) levels of `err.cause` looking for
   Postgres `UNIQUE_VIOLATION` code `'23505'` (apps/web/src/lib/data/sessions.ts:42) matched
   against the `ONE_LIVE_PER_TASK_IDX` constraint name, only falling back to a message substring
   check when the error is already coded as a unique violation — the comment
   (apps/web/src/lib/data/sessions.ts:48-54) explains this avoids a false 409 if a user prompt
   happens to mention the index name. This function is used only in `createAgentSession`
   (apps/web/src/lib/data/sessions.ts:65-89), not in `claimNextSession`, so it protects against
   duplicate mission launches on a card, a distinct concern from claim ownership.

## Inferred / not directly verified

- The claim tests use a hand-rolled `db` mock (apps/web/src/lib/data/__tests__/sessions-claim.test.ts:16-58)
  that stubs `select`/`update`/`transaction` chains rather than hitting Postgres, so the SKIP
  LOCKED and unique-violation behavior described above is verified against the query-builder
  output (compiled SQL/params), not against a live database — real Postgres locking semantics
  are inferred from the driver-level API calls, not exercised end-to-end in this test file.
