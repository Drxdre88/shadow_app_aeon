## Findings (VERIFIED — read directly from the cited files)

1. **`claimNextSession`'s claim query is a user-scoped, card-linked, row-locked security boundary, not a plain filter.** The `WHERE` clause requires the caller's own `userId` (`apps/web/src/lib/data/sessions.ts:184`, `eq(agentSessions.userId, userId),`), requires a non-null `taskId` so chat/dialogue rows can never be claimed (`apps/web/src/lib/data/sessions.ts:186`, `isNotNull(agentSessions.taskId),`), and locks the selected row with `FOR UPDATE SKIP LOCKED` so concurrent runners don't block each other (`apps/web/src/lib/data/sessions.ts:191`, `.for('update', { skipLocked: true })`). This is exercised by the test's compiled-SQL assertions at `apps/web/src/lib/data/__tests__/sessions-claim.test.ts:114` (`expect(where.sql).toContain('"agent_sessions"."task_id" is not null')`).

2. **`recordSessionResult`'s terminal-status guard lives in the UPDATE's `WHERE` clause, not in a prior read, closing a replay race.** The update that flips a session to its final status is conditioned on `notInArray(agentSessions.status, TERMINAL_STATUSES)` (`apps/web/src/lib/data/sessions.ts:286`), so a second, racing call to the same session matches zero rows instead of re-processing the card. The test locks in the exact compiled predicate at `apps/web/src/lib/data/__tests__/sessions-claim.test.ts:199` (`expect(update.sql).toContain('"agent_sessions"."status" not in ($2, $3, $4, $5)')`).

3. **`createAgentSession`'s one-live-per-task duplicate-launch guard has no coverage in the claim test file.** `createAgentSession` catches insert failures and, via `isOneLivePerTaskViolation` (which walks up to `MAX_CAUSE_DEPTH` nested `.cause` links, `apps/web/src/lib/data/sessions.ts:43` and `apps/web/src/lib/data/sessions.ts:47`), rethrows as `LiveMissionExistsError` at `apps/web/src/lib/data/sessions.ts:87` (`if (isOneLivePerTaskViolation(err)) throw new LiveMissionExistsError()`). A search of `apps/web/src/lib/data/__tests__/sessions-claim.test.ts` for `isOneLivePerTaskViolation`, `createAgentSession`, and `LiveMissionExistsError` returns no matches — despite the file's own header comment describing itself as covering the claim/result security boundary, this particular guard (the one that prevents a duplicate agent launch on the same card) is untested there.

4. **The claim test mocks and asserts on a function (`updateTask`) that `sessions.ts` never imports or calls, making those specific assertions non-informative.** The test imports `updateTask` from `../tasks` and mocks it (`apps/web/src/lib/data/__tests__/sessions-claim.test.ts:65` and `apps/web/src/lib/data/__tests__/sessions-claim.test.ts:68`), then repeatedly asserts `expect(updateTask).not.toHaveBeenCalled()` (e.g. `apps/web/src/lib/data/__tests__/sessions-claim.test.ts:173`). But `sessions.ts`'s own import block (`apps/web/src/lib/data/sessions.ts:1`–`apps/web/src/lib/data/sessions.ts:14`) never imports `./tasks`, and the actual card write in `recordSessionResult` is a direct `tx.update(boardTasks)` call (`apps/web/src/lib/data/sessions.ts:304`) with an inline `sql` jsonb merge — not a call through `updateTask` at all. The `updateTask` assertions therefore always pass trivially and do not exercise any real code path.
