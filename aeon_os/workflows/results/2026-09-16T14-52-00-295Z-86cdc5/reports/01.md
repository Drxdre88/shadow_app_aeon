# Session Claim Ownership — Recon Report

Unique marker: AEON_OS_E2E_2026-09-16T14-52-00-295Z-86cdc5_01

Scope: `apps/web/src/lib/data/sessions.ts` and its focused claim tests in
`apps/web/src/lib/data/__tests__/sessions-claim.test.ts`.

## TL;DR

The Hangar session-claim/result pipeline in `apps/web/src/lib/data/sessions.ts`
enforces three independent ownership/idempotency boundaries, each covered by a
dedicated test: (1) `claimNextSession` scopes the pull-mode dispatch query to
the calling user, card-linked rows only, with `SELECT ... FOR UPDATE SKIP
LOCKED`; (2) `recordSessionResult` guards against replaying a terminal result
onto an already-settled session by putting the guard in the `UPDATE ... WHERE`
clause rather than in a prior read; (3) duplicate-launch protection for
`createAgentSession` relies on a Postgres partial unique index surfaced through
a cause-chain walk (`isOneLivePerTaskViolation`), not an application-level
check-then-insert.

## Findings

### 1. `claimNextSession` is a user- and card-scoped pull-mode claim, observed and test-verified

`claimNextSession` (`apps/web/src/lib/data/sessions.ts:174`) runs inside
`db.transaction` and selects a candidate with a `WHERE` clause requiring
`eq(agentSessions.userId, userId)`, `eq(agentSessions.status, 'queued')`,
`isNotNull(agentSessions.taskId)` (`apps/web/src/lib/data/sessions.ts:186`),
and `inArray(agentSessions.engine, engines)`, ordered by `spawnedAt` ascending
and locked with `.for('update', { skipLocked: true })`
(`apps/web/src/lib/data/sessions.ts:191`). The comment directly above the
function (`apps/web/src/lib/data/sessions.ts` lines preceding 174) states the
`taskId IS NOT NULL` predicate is mandatory because kairos-chat/dialogue
sessions share this table and must never be claimed as missions.

VERIFIED by test: `apps/web/src/lib/data/__tests__/sessions-claim.test.ts:102`
("claims a queued, card-linked session for the calling user only") compiles
the captured `WHERE` SQL and asserts `"agent_sessions"."user_id" = $1`,
`"agent_sessions"."status" = $2`, `"agent_sessions"."task_id" is not null`,
and that the params never include another user's id. A companion test at
`apps/web/src/lib/data/__tests__/sessions-claim.test.ts:120` asserts
`captures[0].forArgs` equals `['update', { skipLocked: true }]`, confirming
the row-lock discipline that lets multiple runners poll concurrently without
blocking on each other.

### 2. Engine filtering defaults to all three claimable engines but is caller-narrowable

`CLAIMABLE_ENGINES` is defined as `['claude', 'codex', 'copilot']`
(`apps/web/src/lib/data/sessions.ts:14`), and `claimNextSession`'s third
parameter `engines: HangarAgent[] = CLAIMABLE_ENGINES`
(`apps/web/src/lib/data/sessions.ts:174`-`178`) feeds directly into the
`inArray(agentSessions.engine, engines)` predicate. Tests confirm both ends:
`apps/web/src/lib/data/__tests__/sessions-claim.test.ts:129` ("narrows the
claim to the engines the runner asked for") calls
`claimNextSession(USER_ID, WORKER, ['codex'])` and asserts the compiled SQL
contains a single-value `in ($3)` bound to `'codex'`, while
`apps/web/src/lib/data/__tests__/sessions-claim.test.ts:141` ("defaults to
every claimable engine") asserts the default call binds
`['claude', 'codex', 'copilot']` in that order. This means a runner
requesting a narrower engine set cannot accidentally claim sessions for
engines outside its declared allowlist, and the ordering of the default array
is part of the tested contract (positional param assertions).

### 3. `recordSessionResult`'s terminal-replay guard lives in the UPDATE WHERE, not a prior read — race-safe by construction

`recordSessionResult` (`apps/web/src/lib/data/sessions.ts:249`) reads the
session first, then inside `db.transaction` runs an `UPDATE` whose `WHERE`
clause is `and(eq(agentSessions.id, sessionId),
notInArray(agentSessions.status, TERMINAL_STATUSES))`
(`apps/web/src/lib/data/sessions.ts:286`), where `TERMINAL_STATUSES =
['succeeded', 'failed', 'killed', 'timeout']`
(`apps/web/src/lib/data/sessions.ts:9`). The inline comment states this is
deliberate: a prior read-then-write check would let two racing result posts
both pass, whereas Postgres resolves the race in the `UPDATE` itself — the
loser's statement matches zero rows and the function returns early
(`if (!updatedSession) return { session, task: null, guarded: true }`).

VERIFIED by test: `apps/web/src/lib/data/__tests__/sessions-claim.test.ts:191`
("carries the terminal-status guard in the UPDATE, not in a prior read")
compiles the captured update `WHERE` and asserts it contains
`"agent_sessions"."status" not in ($2, $3, $4, $5)` with params
`[SESSION_ID, 'succeeded', 'failed', 'killed', 'timeout']`. A second test at
`apps/web/src/lib/data/__tests__/sessions-claim.test.ts:203` ("processes the
card exactly once when two result posts race") simulates a winner/loser pair
against a shared `running` session snapshot and asserts the card-metadata
patch and `touchProject` call each fire exactly once even though both calls
read the same pre-race row.

### 4. Duplicate-launch protection is a Postgres partial unique index, detected via a bounded cause-chain walk (not string matching alone)

`createAgentSession` (`apps/web/src/lib/data/sessions.ts:63`) wraps the insert
in a `try/catch` and, on failure, calls `isOneLivePerTaskViolation(err)`
(`apps/web/src/lib/data/sessions.ts:87`) before throwing
`LiveMissionExistsError` (`apps/web/src/lib/data/sessions.ts:29`).
`isOneLivePerTaskViolation` (`apps/web/src/lib/data/sessions.ts:45`) walks up
to `MAX_CAUSE_DEPTH` (`= 5`, `apps/web/src/lib/data/sessions.ts:43`) levels of
`err.cause`, checking `candidate.code === UNIQUE_VIOLATION` ('23505') and only
then matching `candidate.constraint === ONE_LIVE_PER_TASK_IDX`
(`= 'agent_sessions_one_live_per_task_idx'`,
`apps/web/src/lib/data/sessions.ts:36`) or a message substring — a bare
message substring check without the `code` gate is explicitly called out in
the surrounding comment (`apps/web/src/lib/data/sessions.ts` lines 38-42) as
unsafe on drizzle >= 0.38, since it quotes failed-insert params (goal, prompt,
metadata) into the outer error message, which could otherwise let a prompt
naming the index string trigger a false 409. This is a cross-surface guard: a
top-of-file comment (`apps/web/src/lib/data/sessions.ts:83`-`85`, near the
catch block) states the partial unique index (migration 0033) is what closes
the check-then-insert race for both the REST and MCP spawn surfaces, which
never ran an app-level "is there already a live session" check.

INFERRED (not directly observed in this scope): the `sessions-claim.test.ts`
file does not contain a test exercising `createAgentSession` /
`isOneLivePerTaskViolation` / `LiveMissionExistsError` — its test suite (lines
102-268, per grep above) covers only `claimNextSession`,
`recordSessionResult`, `scrubPgText`, and `scrubJsonb`. Coverage for the
one-live-per-task guard, if it exists, lives outside this focused claim test
file and was not located within this bounded scope.
