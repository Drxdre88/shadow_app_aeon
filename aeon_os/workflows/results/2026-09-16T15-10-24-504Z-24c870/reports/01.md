## Findings

### 1. `claimNextSession` enforces per-user, card-linked, engine-scoped pull-mode dispatch inside a single transaction (VERIFIED)

`claimNextSession` (apps/web/src/lib/data/sessions.ts:174) selects one candidate row with `eq(agentSessions.userId, userId)`, `eq(agentSessions.status, 'queued')`, `isNotNull(agentSessions.taskId)` (apps/web/src/lib/data/sessions.ts:186), and `inArray(agentSessions.engine, engines)`, then locks it with `.for('update', { skipLocked: true })` (apps/web/src/lib/data/sessions.ts:191) before flipping it to `running` in the same `db.transaction`. The `isNotNull(agentSessions.taskId)` predicate is the ownership boundary that keeps kairos-chat/dialogue rows (which share the `agent_sessions` table but have no `taskId`) from ever being claimed, per the comment at apps/web/src/lib/data/sessions.ts:169-173. This is corroborated by the test `'claims a queued, card-linked session for the calling user only'` (apps/web/src/lib/data/__tests__/sessions-claim.test.ts:88), which asserts the compiled WHERE clause contains `"agent_sessions"."task_id" is not null` and that the bound params never include another user's id.

### 2. Terminal-state replay protection for `recordSessionResult` lives in the UPDATE's WHERE clause, not in a prior read (VERIFIED)

`recordSessionResult` (apps/web/src/lib/data/sessions.ts) guards its session-flip UPDATE with `notInArray(agentSessions.status, TERMINAL_STATUSES)` at apps/web/src/lib/data/sessions.ts:286, where `TERMINAL_STATUSES` is defined at apps/web/src/lib/data/sessions.ts:17 as `['succeeded', 'failed', 'killed', 'timeout']`. Because the check is expressed as a SQL predicate on the UPDATE itself (not a `SELECT` followed by a conditional `UPDATE`), two racing result-posts for the same session cannot both succeed: the loser's UPDATE matches zero rows. This is exercised by the test `'processes the card exactly once when two result posts race'` (apps/web/src/lib/data/__tests__/sessions-claim.test.ts:200), which simulates a winner (session flips, card patched, `touchProject` called once) followed by a loser whose update returns no rows, and asserts `cardUpdates()` and `touchProject` call counts stay at 1 after both attempts.

### 3. The claim tests mock a `../tasks` module and its `updateTask` export that `sessions.ts` never imports or calls, making the four `expect(updateTask).not.toHaveBeenCalled()` assertions structurally unable to fail (VERIFIED code fact; INFERRED test-design gap)

The test file mocks `'../tasks'` and imports `updateTask` from it (apps/web/src/lib/data/__tests__/sessions-claim.test.ts:65 and :68), then asserts `expect(updateTask).not.toHaveBeenCalled()` in four places: apps/web/src/lib/data/__tests__/sessions-claim.test.ts:173, :187, :234, and :245. However, `apps/web/src/lib/data/sessions.ts` contains no import of `./tasks` or `updateTask` anywhere in the file — `recordSessionResult`'s card write is performed directly via `tx.update(boardTasks)...` inside the transaction, not through a `tasks.ts` helper. A comment at apps/web/src/lib/data/sessions.ts:315 references `updateTask` only rhetorically ("same as updateTask would have emitted"), not as an actual call site. Consequence (INFERRED): these four assertions pass unconditionally regardless of whether the card-write logic is correct, so they provide no real regression coverage for "no card write happened" — the tests' actual coverage for that behavior comes instead from the `cardUpdates()` helper (apps/web/src/lib/data/__tests__/sessions-claim.test.ts:82-84) used elsewhere in the same file (e.g. apps/web/src/lib/data/__tests__/sessions-claim.test.ts:213, :219).

### 4. Unique-violation detection for the one-live-mission-per-task guard walks a bounded `cause` chain rather than trusting `err.message` alone (VERIFIED)

`isOneLivePerTaskViolation` (apps/web/src/lib/data/sessions.ts, defined starting at line 46, loop at apps/web/src/lib/data/sessions.ts:47) iterates up to `MAX_CAUSE_DEPTH = 5` (apps/web/src/lib/data/sessions.ts:43) levels of `err.cause`, only matching on the `message` substring `ONE_LIVE_PER_TASK_IDX` (apps/web/src/lib/data/sessions.ts:36, `'agent_sessions_one_live_per_task_idx'`) when `candidate.code === UNIQUE_VIOLATION` (`'23505'`, apps/web/src/lib/data/sessions.ts:41) is also true, per the guard at apps/web/src/lib/data/sessions.ts:52-56. `createAgentSession` (apps/web/src/lib/data/sessions.ts:70) calls this helper at apps/web/src/lib/data/sessions.ts:87 and converts a match into a `LiveMissionExistsError` (apps/web/src/lib/data/sessions.ts:29-33) so REST/MCP spawn callers get a typed 409-style error instead of an opaque 500 from a nested/pooled driver error.

The characterization of the assertions as providing "no real regression coverage" is an INFERENCE from those facts, not a runtime observation (no tests were executed as part of this recon).
