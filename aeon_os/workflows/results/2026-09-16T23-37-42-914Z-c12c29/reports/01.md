### 1. Observed — `claimNextSession` restricts the claim predicate to the caller's own queued, card-linked sessions and locks the candidate row for update

`apps/web/src/lib/data/sessions.ts:183` binds the WHERE clause to

select is then locked with `apps/web/src/lib/data/sessions.ts:191`

`captures[0].forArgs` equals `['update', { skipLocked: true }]`.

### 2. Observed — the terminal-status replay guard for `recordSessionResult` is expressed in the UPDATE's WHERE clause, not in a preceding read

`apps/web/src/lib/data/sessions.ts:284` opens the `.where(and(` for the
session-flip UPDATE inside the transaction, `apps/web/src/lib/data/sessions.ts:285`
adds `eq(agentSessions.id, sessionId)`, and
`apps/web/src/lib/data/sessions.ts:286` adds
`notInArray(agentSessions.status, TERMINAL_STATUSES)` to that same predicate.
`apps/web/src/lib/data/sessions.ts:289` checks `if (!updatedSession) return { session, task: null, guarded: true }` —
i.e. the function's fallback path is reached whenever the UPDATE matches zero
rows.

Inference: because the guard condition is a clause on the row being updated
rather than a value read earlier in the function, two concurrent calls
updating the same `sessionId` cannot both match — Postgres resolves which one
(if either) affects a row — so at most one caller proceeds to the card-write
branch. The cited lines show the predicate and the zero-match fallback; they
do not by themselves demonstrate transaction isolation semantics, which is a
property of Postgres/Drizzle rather than of this file.

### 3. Observed — `isOneLivePerTaskViolation` requires a coded `unique_violation` before it will match on constraint name or message text, walking `err.cause`

`apps/web/src/lib/data/sessions.ts:45` declares
`function isOneLivePerTaskViolation(err: unknown): boolean {`.
`apps/web/src/lib/data/sessions.ts:54` gates the match with
`if (candidate.code === UNIQUE_VIOLATION) {` — the constraint-name and
message-substring checks are nested inside this `if`, so they only execute
once the coded check has passed. `apps/web/src/lib/data/sessions.ts:58`
reassigns `cursor = candidate.cause`, advancing the loop to the next nested
error on each iteration up to `MAX_CAUSE_DEPTH`.

Inference: gating the substring/constraint check behind `candidate.code ===
UNIQUE_VIOLATION` means an insert failing for an unrelated reason cannot be
misclassified as a duplicate-launch conflict merely because its error message
happens to contain the index name (for example inside a quoted query
parameter) — only errors already carrying the Postgres unique-violation code
reach that check. The cited lines show the gating structure and the cause
walk; they do not themselves prove what a live Postgres driver emits for any
particular failure mode.
